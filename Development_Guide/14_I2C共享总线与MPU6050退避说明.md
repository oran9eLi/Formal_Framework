# I2C共享总线与MPU6050退避说明

## 1. 现象

BME280和MPU6050共用同一条硬件I2C总线：

- I2C外设：I2C1
- SCL：PB6
- SDA：PB7
- 当前总线速率：100 kHz

实际运行时出现：

- MPU6050上电运行一段时间后离线。
- BME280会短暂离线，随后又恢复。
- 屏幕上看起来像BME280和MPU6050互相影响。

这个现象不是屏幕显示变量冲突，而是共享I2C总线被异常MPU6050访问牵连。

## 2. 原因分析

当前采集周期如下：

- MPU6050：每10 ms采集一次。
- BME280：每1000 ms采集一次。
- MPU6050单次I2C访问超时：20 ms。

当MPU6050运行中发生I2C错误时，如果没有退避机制，采集任务会在下一个10 ms周期继续访问MPU6050。若故障持续，就会出现：

1. MPU6050读失败。
2. 10 ms后再次读MPU6050。
3. 反复触发I2C超时或BUSY。
4. BSP层对整条I2C执行恢复。
5. BME280也在同一条I2C上，因此短时间被影响。
6. BME280下一次读成功后又恢复在线。

所以BME280“一会断一下又好了”，本质上是MPU6050故障访问对共享I2C的干扰。

## 3. 本次软件修改

本次修改在Framework采集调度层加入MPU6050失败退避。

修改文件：

- `Framework/Inc/px4lite_config.h`
- `Framework/Src/px4lite_modules.c`
- `Sensor/Src/sensor_mpu6050.c`

新增配置：

```c
#define PX4LITE_IMU_ERROR_BACKOFF_MS     1000U
```

策略：

- MPU6050正常时，仍按`PX4LITE_IMU_WORK_PERIOD_MS`每10 ms采集一次。
- MPU6050发生`PX4LITE_IO_ERROR`后，暂停访问MPU6050 1000 ms。
- 退避期间不再高频访问异常MPU6050，减少对BME280的影响。
- MPU6050单次读失败后，驱动内部清除初始化标志。
- 下次退避结束后，会重新探测地址、检查WHO_AM_I并重新配置寄存器。
- 下次采集成功后，清除退避状态，恢复正常10 ms采集。

## 4. 修改后的预期行为

MPU6050稳定时：

- 姿态数据正常更新。
- BME280温度、湿度、气压正常更新。

MPU6050异常或掉线时：

- MPU6050会被判为离线。
- Framework每1000 ms尝试一次重新初始化和恢复读取。
- BME280不再被MPU6050每10 ms的失败访问持续干扰。
- 屏幕上BME280状态应更稳定。

## 5. 硬件仍需检查

软件退避只能降低异常MPU6050对总线的影响，不能修复硬件电气问题。仍需重点检查：

1. SDA/SCL是否各有一组4.7k左右上拉到3.3V。
2. 不要把SDA/SCL上拉到5V。
3. BME280和MPU6050的VCC/GND都应直接接到主板公共电源和公共地。
4. MPU6050的AD0不要悬空，应固定接GND或VCC。
5. 杜邦线尽量短，避免接触不良。
6. MPU6050模块旁边建议增加0.1 uF和10 uF去耦电容。

## 6. 验证方法

1. 保持BME280和MPU6050都接在I2C1 PB6/PB7。
2. 上电运行，观察屏幕自检状态和飞行数据页。
3. 等待MPU6050复现离线。
4. 观察BME280温度、湿度、气压是否还会频繁断续。
5. 若BME280稳定，说明退避策略有效。
6. 若BME280仍频繁断续，优先检查上拉、电源、接地和模块接触。

## 7. 注意

该修改不会改变屏幕显示变量映射：

- MPU6050仍对应横滚、俯仰、偏航和MPU6050自检状态。
- BME280仍对应温度、湿度、气压和BME280自检状态。

两者在屏幕显示层不冲突，问题发生在共享I2C采集层。
