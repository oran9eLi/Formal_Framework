# Formal Framework 移植进度与功能清单

## 1. 文档用途

本文件是 `Formal_Framework` 的持续更新台账，用于回答以下问题：

- 当前从原工程移植了哪些代码和硬件能力。
- 哪些功能已经真实运行，哪些只是接口或占位。
- 当前阶段是否完成以及完成依据。
- 下一阶段需要实现什么以及如何验收。

开发人员不得仅凭目录、任务或函数已经存在，就把对应功能标记为完成。
功能只有在真实实现、调用链闭合并通过规定验证后，才能标记为“完成”。

## 2. 当前阶段结论

### 2.1 架构迁移第一阶段：已完成

第一阶段目标是形成独立工程、固定基础数据边界并跑通 GNSS 最小闭环。
截至 2026-06-10，以下内容已经完成：

- `Formal_Framework` 不依赖原工程源码目录，可独立使用 ARMCC5 编译。
- HAL、CMSIS、FreeRTOS 依赖已经收拢到本工程 `Third_Party`。
- 自研代码按 `Bsp`、`Sensor`、`Framework`、`Business`、`Debug` 分层。
- USART2 DMA + IDLE 到 GNSS NMEA 解析链路已经跑通。
- GPS 和北斗 GGA、RMC、GSA、GSV 数据已经进入统一 GNSS 快照。
- GNSS 旧通用兼容层已删除，只保留强类型快照和 Framework 适配链。
- GNSS Measurement topic 到 Navigation domain topic 的转换链路已经建立。
- 应用层通过只读 API 获取完整导航快照和系统状态。
- 状态、时间戳、数据有效性、质量和故障码已有第一版统一定义。
- 六个基础任务、任务心跳、栈溢出和内存分配失败 hooks 已建立。
- 第一阶段代码曾通过 ARMCC 5.06 全量编译，结果为
  `0 Error / 0 Warning`。

第一阶段完成后，后续已经继续补齐普通传感器读取、RTC 时间保持、
显示、LoRa 遥测发送、日志显示、SD 存储链路和四路电机 PWM 控制基础闭环。
当前真实完成度以第 3 节功能清单为准。

## 4. 当前正式运行流程

```text
ATGM336H
   |
USART2 DMA + IDLE
   |
BSP 接收缓冲区
   |
GNSS 驱动解析 GGA/RMC/GSA/GSV
   |
GNSS 强类型快照
   |
Platform Adapter
   |
GNSS Measurement Topic
   |
Estimator 基础转换
   |
Navigation Domain Topic
   |
App_CopyNavigation / App_CopySystem
   |
Business、Display、LoRa、Logger、Storage 等消费者
```

电机控制基础闭环：

```text
Display Motor 页触摸滑条 / 急停
   |
App_SetMotorThrottlePercent / App_CopyMotor
   |
Framework Control task
   |
Platform Adapter
   |
BSP PWM / BSP Button
   |
TIM3 PA6/PA7、TIM4 PD12/PD13 四路 PWM 输出
```

约束：

- BSP 只处理硬件和字节传输。
- Sensor 只处理设备协议、解析、标定和设备状态。
- Sensor 对外发布设备专属强类型快照，不使用通用数值通道模拟不同字段。
- Framework 负责调度采集、发布、状态和通用数据通道。
- Business 只通过应用 API 读取快照，不直接访问 BSP、DMA 或驱动私有变量。
- 通信层必须序列化并生成完整帧，禁止直接发送 C 结构体内存。
- Control 任务是电机 PWM 的唯一写入者，Business 和 Display 只能通过 `app_data_api.h` 写入目标油门或读取电机快照。

## 5. 剩余开发步骤

### 阶段 2：完成基础系统闭环

任务：

1. 完成函数级文档，覆盖自研公开接口和关键内部函数。
2. 固定模块注册、初始化、自检、启动、停止和恢复接口。
3. 实现 POST 结果汇总和启动状态快照。
4. 完成告警恢复动作和输出动作。
5. 扩展 Health Monitor，加入任务、队列、栈、heap 和 deadline 监控。

验收：

- 自研公开接口具有用途、参数、返回值和上下文说明。
- 上电后可以区分启动中、正常、降级和失败。
- 单个模块故障不会阻塞其他模块启动。
- 多个告警同时存在时由最高严重度决定输出，且告警动作可追踪、可恢复。

### 阶段 3：接入 IMU、气压计和电源数据（已完成）

任务：

1. 按固定模板接入 MPU6050 或正式 IMU。
2. 接入气压计和电池电压、电流数据。
3. 定义原始值、标定值、工程值和质量字段。
4. 高频数据使用 FIFO，低频状态使用 latest-value topic。
5. 为每类数据定义采样时间、发布时间、最大年龄和超时状态。

验收：

- 每个驱动只有一个采集所有者。
- 不读半包、不发布半包、不复制撕裂快照。
- 采集任务长期运行无明显周期漂移。
- 断线、恢复、总线错误和数据过期可被检测。

### 阶段 4：完成运算和融合（基础姿态估计已完成）

当前代码已经完成 GNSS 到 Navigation 的基础转换，以及 IMU 一阶互补滤波得到 roll/pitch 和相对 yaw。下列任务仍属于未完成的完整融合范围。

任务：

1. 完成 IMU 标定、坐标系转换和绝对航向约束。
2. 实现气压高度、垂直速度和滤波。
3. 对齐 GNSS、IMU 和气压计采样时间。
4. 增加范围、变化率、跳变和质量过滤。
5. 发布带有效位和置信度的融合导航快照。

验收：

- 未计算字段不得标记有效。
- 时间未对齐的数据不得直接融合。
- 单一数据源失效时进入定义好的降级状态。

### 阶段 5：完成应用和外部输出（显示、LoRa 发送、日志显示、存储和电机基础控制已完成）

任务：

1. Display 已接入页面模型和业务数据显示。
2. 日志显示和 SD 存储链路已完成。
3. LoRa 遥测发送已接入当前快照数据。
4. Motor 页和 Control 基础链路已接入，当前控制量为目标油门 PWM。
5. 5G 和 Remote ID 后续复用通信/快照边界接入。
6. Command 模块后续负责 LoRa RX 命令分发、执行和 ACK 闭环。
7. 所有消费者只读取应用快照或订阅事件。

验收：

- 显示、日志和通信读取的是同一版本的完整快照。
- 通信链路不会发送半帧，接收端可以发现丢包、乱序和 CRC 错误。
- 慢速外设不会阻塞采集和融合任务。

### 阶段 6：可靠性和产品化

任务：

1. 实现任务心跳门控的 IWDG。
2. 保存 HardFault、栈溢出、malloc 失败和复位原因。
3. 加入参数、标定、版本、Bootloader 和升级机制。
4. 完成 24/72 小时稳定性、故障注入和硬件在环测试。
5. 定义未来 Linux A 核 IPC 协议并保证 MCU 可独立运行。

验收：

- 关键任务失联后停止喂狗，并能在重启后读取故障原因。
- 队列满、DMA 停滞、传感器离线和 SD 写失败均可定位。
- 发布包包含固件、构建日志、版本信息和校验值。

## 6. 每次移植必须记录的内容

每加入一个模块，必须在本文件和 `Change_History` 中记录：

1. 模块名称、型号、总线、引脚、DMA、中断和资源占用。
2. 从哪个工程或版本移植，保留和删除了哪些内容。
3. BSP、Driver、Framework、Business 各层新增接口。
4. 发布的数据类型、单位、坐标系、频率和最大年龄。
5. 模块状态、故障码、超时、恢复和降级规则。
6. 任务所有者、调用周期、栈水位和最长执行时间。
7. 队列、FIFO、topic、静态 buffer 的所有权和容量。
8. 调试功能及关闭调试后不影响正式逻辑的证明。
9. 编译、台架、断线恢复、长稳和故障注入结果。
10. 当前未完成项和下一位开发者的接续入口。

## 7. 状态标记规则

| 标记 | 含义 |
|---|---|
| 完成 | 真实实现、调用链闭合、通过验收 |
| 基础完成 | 主流程可运行，但算法、覆盖或异常处理不完整 |
| 骨架完成 | 接口和结构存在，尚无完整消费者或业务闭环 |
| 占位 | 为保持架构和编译而存在，不提供真实设备功能 |
| 预留 | 只有设计边界，尚未进入代码实现 |
