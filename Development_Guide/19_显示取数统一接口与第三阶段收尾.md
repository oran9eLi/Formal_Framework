# 显示取数统一接口与第三阶段收尾

本文记录 LoRa 远程显示剩余两项工作的方案与**实施顺序**：

1. **统一显示取数接口**：无论 LOCAL 还是 REMOTE 模式，显示屏都用同一套 API 取数据，模式判断与远端归一只存在于一处。
2. **接收端同步消息日志与完整告警表**（协议/带宽细节见 `18_LoRa远程显示第三阶段显示同构方案.md`）。

第二件事依赖第一件事，且当前另有一路在用 **LVGL** 重做显示界面，因此**统一取数接口必须先行、尽早冻结签名**。

## 1. 背景与排序结论

显示屏存在两个并行消费者：现有自绘显示(`display.c` + `display_pages.c`)和正在重做的 LVGL 界面。两者都要"按当前模式取该显示的数据"。这套取数逻辑现在散在 `Display_PrepareSnapshot()` 里——LOCAL 走 `App_CopyNavigation/...`，REMOTE 走 `App_CopyRemoteTelemetry` + `Display_LoadRemoteTelemetrySnapshot()` 归一。

| 若不先统一 | 后果 |
|---|---|
| LVGL 直接耦合 `App_Copy*` + 模式分支 | LOCAL/REMOTE 判断被复制成两套，后续改一处要改两处 |
| LVGL 依赖老显示的 HMI 变量缓存 | 把老显示内部实现变成跨界依赖，LVGL 无法独立演进 |
| 等 LVGL 硬化后再统一 | 需同时改两套 UI 并调和两条数据路径，成本陡增 |

**结论(排序)**：

```text
1) 统一显示取数接口  —— 紧急(LVGL 并行)，先冻结签名，再实现
2) 日志/完整告警表同步 —— 随后，作为新 RemoteTelemetry 字段被统一接口 surface 出来
```

排序依据符合仓库规则优先级：数据正确性 > 故障可检测性 > 实时性 > 功能数量 > 开发便利性。统一接口属于"故障可检测性/可维护性"基础设施，日志同步属于"功能数量"。

## 2. 设计原则

1. **显示层是纯消费者**：`display.c`、LVGL widget、`display_pages.c` 都不判 LOCAL/REMOTE，不直接读 Framework topic 或 `RemoteTelemetry`。
2. **模式解析唯一一处**：LOCAL/REMOTE 选择与远端→本机结构体归一只存在于 App 层统一接口内部。
3. **每个域一种结构体**：复用现有 `App_*Snapshot_t`，不区分"本机结构体/远端结构体"。归一目标已存在——`Display_LoadRemoteTelemetrySnapshot()` 现在就是把远端快照塞进 `App_NavigationSnapshot_t` 的形状。
4. **本机白名单字段不随模式变**：模式标识、本机 LoRa 状态灯、TX/RX 计数、丢包率永远取本机，不走模式解析。
5. **可移植到 LVGL**：共享契约是**结构体级 API**，不是老显示的 HMI 变量缓存。
6. **MCU 约束**：无动态分配；按 `biz_display`(10ms) 周期构建一次，预算可控。

## 3. 统一显示取数 API

放在 Business/App 层(`app_data_api.h` 扩展，或紧贴它的 `app_display_source.c`)。它同时能拿到本机 `App_Copy*` 与 `App_CopyRemoteTelemetry`，对显示层暴露**模式无关**的取数入口。

### 3.1 模式解析域(按当前模式自动选源)

```c
/* 内部判 LOCAL/REMOTE，调用方不感知数据来源；返回值统一表达新鲜度。 */
Px4Lite_Result_t App_GetDisplayNavigation(App_NavigationSnapshot_t *out, uint32_t now_ms);
Px4Lite_Result_t App_GetDisplayEnvironment(App_EnvironmentSnapshot_t *out, uint32_t now_ms);
Px4Lite_Result_t App_GetDisplaySystem(App_SystemSnapshot_t *out, uint32_t now_ms);
Px4Lite_Result_t App_GetDisplayAlarm(App_AlarmSnapshot_t *out, uint32_t now_ms);
Px4Lite_Result_t App_GetDisplayMotor(App_MotorSnapshot_t *out, uint32_t now_ms);
Px4Lite_Result_t App_GetDisplayDateTime(App_DateTimeSnapshot_t *out, uint32_t now_ms);
Px4Lite_Result_t App_GetDisplayMessageLog(App_DisplayLogSnapshot_t *out, uint32_t now_ms);
```

返回值语义(统一新鲜度口径，UI 据此渲染)：

| 返回值 | 含义 | UI 应表现 |
|---|---|---|
| `PX4LITE_OK` | 当前模式下数据新鲜 | 正常显示 |
| `PX4LITE_STALE` | 已收到但超过刷新窗口 | 保留最后值并标 stale，不清零 |
| `PX4LITE_NOT_READY` | 从未收到 | 显示无效/清零 |

> REMOTE 模式下断链即对应域返回 `STALE`/`NOT_READY`；显示不自动切回本机主数据，未收字段显 0 或无效(与 doc 17/18 口径一致)。

各 getter 的落地工作量并不相同(核对 `display.c` 现有 `Display_LoadRemote*`)，**签名可一次冻结，但实现要分批**：

| getter | 远端归一现状 | 工作量 |
|---|---|---|
| `App_GetDisplayNavigation` / `App_GetDisplayEnvironment` / `App_GetDisplayMotor` | 已构建对应 `App_*Snapshot_t`(`display.c:1038-1096`) | 纯包装 |
| `App_GetDisplayDateTime` / `App_GetDisplaySystem` | 现直接写 HMI、未经 App 结构(`:1080`、`:1305`) | 需新增小～中归一(数据已在远端快照) |
| `App_GetDisplayAlarm` | 远端只有摘要 `highest_*`，无 `records[]` | 摘要可立即，整表**依赖第二件事** |
| `App_GetDisplayMessageLog` | 日志是 Display 内部概念，REMOTE 仍取本机 | 净新增，**与第二件事(doc 18 §5)合并落地** |

### 3.2 本机白名单域(永远本机来源)

```c
typedef struct {
  uint32_t tx_frame_count;  /**< 本机 LoRa 发送完成帧数。 */
  uint32_t rx_frame_count;  /**< 本机 LoRa 接收帧数。 */
  uint16_t loss_permille;   /**< 接收链路丢包率，单位 ‰(0~1000)，见 px4lite_mavlink_rx.c。 */
  uint8_t  lora_state;      /**< 本机 LoRa 模块公开状态(状态灯)。 */
  uint8_t  reserved;        /**< 对齐保留。 */
} App_DisplayLinkStatus_t;

void                 App_GetDisplayLinkStatus(App_DisplayLinkStatus_t *out, uint32_t now_ms);
Px4Lite_RemoteMode_t App_GetRemoteDisplayMode(void); /* 已存在，UI 用于模式标识 */
```

这些字段在 REMOTE 模式下仍取本机：丢包率/链路灯反映的是**显示端自己**的链路健康，不取远端值。丢包率已落地(`App_GetCommStats` → `rx_loss_permille`)，作为"链路诊断保持本机来源"的样板。

### 3.3 可选便利封装

LVGL 倾向在每个 widget 刷新回调里按需取数，per-域 getter 更友好；老显示倾向每周期整批构建。可在 getter 之上加一个便利封装，但**契约以 per-域 getter 为准**：

```c
typedef struct {
  App_NavigationSnapshot_t  navigation;
  App_EnvironmentSnapshot_t environment;
  App_SystemSnapshot_t      system;
  App_AlarmSnapshot_t       alarm;
  App_MotorSnapshot_t       motor;
  App_DateTimeSnapshot_t    date_time;
  App_DisplayLogSnapshot_t  message_log;
  App_DisplayLinkStatus_t   link;        /* 本机白名单 */
  Px4Lite_RemoteMode_t      mode;
  uint32_t                  ready_mask;  /* 各域 OK 位 */
  uint32_t                  stale_mask;  /* 各域 STALE 位 */
} App_DisplayModel_t;

void App_BuildDisplayModel(App_DisplayModel_t *out, uint32_t now_ms); /* 内部即逐个调用 3.1/3.2 */
```

## 4. 分层与数据流

```text
Framework topics + RemoteTelemetry
  └─ app_data_api：App_Copy*（本机） / App_CopyRemoteTelemetry（远端）
       └─ 统一取数：App_GetDisplay*  ← 模式解析 + 远端归一 + valid/stale（唯一一处）
            ├─ 老显示 display.c：消费结构体后回填自身 HMI 缓存 ─┐
            └─ LVGL widget 刷新：直接消费结构体               ─┘ 均不判模式
                 └─ display_pages.c / LVGL 布局：只绘制，不取数、不判模式
```

迁移动作：

| 从 | 移到 |
|---|---|
| `Display_PrepareSnapshot()` 内的 LOCAL/REMOTE 分支(现 `display.c:1552-1614`) | App 层 `App_GetDisplay*` 内部 |
| `App_CopyRemoteTelemetry` + `Display_LoadRemoteTelemetrySnapshot()` 远端归一 | App 层 `App_GetDisplay*` 内部 |
| `display.c` 直接调 `App_Copy*` | 改调 `App_GetDisplay*` |

## 5. 与 LVGL 并行的落地策略

1. **先冻结签名再实现**：与做 LVGL 的人先敲定 §3 的结构体形状与函数签名并冻结；LVGL 照此对接，实现可在背后跟进。
2. **可迁移域先行**：nav/env/motor 是纯包装(REMOTE 已归一到 `App_*Snapshot_t`)，可立即搬、行为不变；datetime/system 顺带补上小归一。alarm/log 的 getter 签名同时冻结，但 REMOTE 实现先返回当前行为(告警摘要 / 本机日志)，待第二件事补齐远端数据后再切换——签名不变,两套 UI 无感。
3. **LVGL 不依赖 HMI 缓存**：LVGL 只读 §3 的结构体；HMI 变量缓存退回为老显示内部实现。
4. **避免移动靶**：API 签名一旦冻结尽量不动；内部实现变化不影响 LVGL。

## 6. 第二件事：消息日志与完整告警表同步

协议载荷、带宽预算与丢包语义已在 `18_LoRa远程显示第三阶段显示同构方案.md` 第 5/6/7 节定稿，要点：

- 用 `V2_EXTENSION`/`TUNNEL` 打包多行，**禁止** `NAMED_VALUE_INT` 逐行(约 840 B/s 溢出)。
- 消息日志为枚举编码(每条约 8 字节)，增量 + `LOGSEQ` 心跳；有损无 ARQ，允许序号空洞。
- 常态总发送负载控制在 ~550 B/s(<60% UART)。

在本文框架下，这件事落地为：

1. `RemoteTelemetry` 增加完整告警表行与消息日志结构化字段(接收端写入)。
2. `App_GetDisplayAlarm`/`App_GetDisplayMessageLog` 在 REMOTE 模式返回这些远端字段，在 LOCAL 模式返回本机告警表/本机日志。
3. 两套 UI 经统一接口**自动获得**，不各自接协议——这正是统一接口先行的复利。

## 7. 实施顺序

**阶段 A（统一接口，可立即，不依赖第二件事）：**

1. 冻结 §3 全量头文件签名(`App_GetDisplay*` / `App_DisplayLinkStatus_t` / `App_DisplayLogSnapshot_t`)，与 LVGL 对接。
2. 实现 nav/env/motor 纯包装；为 datetime/system 新增远端→`App_*Snapshot_t` 小归一；`App_GetDisplayLinkStatus` 复用 `App_GetCommStats`。
3. `App_GetDisplayAlarm` 返回摘要、`App_GetDisplayMessageLog` 返回本机日志(=当前行为)，签名已冻结。
4. `display.c` 改为消费 `App_GetDisplay*`，删除 `Display_PrepareSnapshot()` 内的模式分支；LVGL 对接同一套接口(不碰 HMI 缓存)。
5. 桌面单测覆盖各 `App_GetDisplay*` 在 LOCAL/REMOTE 下的来源与 `OK/STALE/NOT_READY` 口径；核对老显示行为不变。

**阶段 B（补远端数据，与 doc 18 同步合并）：**

6. 定义结构化消息日志 + 完整告警表的 MAVLink 扩展与 `RemoteTelemetry` 字段(doc 18 §5/§6)；接收端写入。
7. 把 `App_GetDisplayAlarm/MessageLog` 的 REMOTE 实现切到远端整表/远端日志(签名不变)；消息日志从 Display 去抖机抽取为业务级结构化日志。
8. Keil Rebuild All，目标 `0 Error(s), 0 Warning(s)`。

## 8. 验收标准

| 验收项 | 通过条件 |
|---|---|
| 单一取数口径 | `display.c` 与 LVGL 取业务数据只经 `App_GetDisplay*`；除模式标识外不含 LOCAL/REMOTE 分支。 |
| 模式解析唯一 | LOCAL/REMOTE 选择与远端归一只存在于 App 层一处，`display_pages.c`/LVGL 布局不判模式。 |
| 本机白名单 | 模式标识、LoRa 状态灯、TX/RX 计数、丢包率在 REMOTE 下仍取本机。 |
| 共用契约 | LVGL 与老显示编译期共用同一套 `App_GetDisplay*` 签名；LVGL 不依赖老显示 HMI 缓存。 |
| 断链表现 | 对应域返回 `STALE` 保留旧值、`NOT_READY` 清零，不自动切回本机主数据。 |
| 远端主数据 | 完成第二件事后，REMOTE 下告警表与消息日志经统一接口来自目标设备。 |
| 实时性预算 | 每 `biz_display` 周期构建无动态分配；新增发送负载符合 doc 18 第 7 节预算。 |
| 构建验证 | Keil Rebuild All 达到 `0 Error(s), 0 Warning(s)`。 |
