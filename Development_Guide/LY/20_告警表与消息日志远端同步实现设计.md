# 完整告警表与消息日志远端同步实现设计

本文是 `18_LoRa远程显示第三阶段显示同构方案.md`「第二件事」与 `19_显示取数统一接口与第三阶段收尾.md`「阶段 B」的**落地实现设计**。统一取数接口(阶段 A)已完成，本文在其之上补齐 REMOTE 模式的两项远端数据：**完整告警表**与**消息日志**。

两项共享同一套打包传输，但**分期实现**：

```text
Part 1  完整告警表同步   —— 先做。契约已定、改动机械，借此打通 TUNNEL 传输。
Part 2  消息日志同步     —— 随后。需先把日志生产者从显示层上提到业务层。
```

## 1. 设计原则

1. **传码不传文字，显示层本地映射**：链路只传枚举/故障码（告警行 `source_id`+`fault_code`，日志 `message_id`），屏幕提示文字由两端各自的 `display_text` 本地映射。两端跑同一套固件，码表天然一致——**前提是把这套枚举当作 append-only 协议契约**（只许尾部追加，不许重排/改号）。
2. **统一接口复利**：显示层只经 `App_GetDisplay*` 取数，已不判 LOCAL/REMOTE。本文只改 App 层 getter 的 REMOTE 实现与 Framework 收发，**两套 UI（老显示 / LVGL）零改动**即获得远端数据。
3. **有损无 ARQ**：链路单向、有损、无内容级重传。允许丢帧造成的序号空洞；断链保留最后远端值并标 `STALE`，不自动回退本机主数据。
4. **MCU 约束**：无动态分配；固定容量缓冲；按 `biz_display`(10ms) / comm 周期构建，预算可控。
5. **打包载体唯一**：完整告警表行、消息日志增量统一用 `TUNNEL` 承载，**禁止** `NAMED_VALUE_INT` 逐行（见 doc 18 §6 带宽分析）。

## 2. 共享传输：TUNNEL 契约

用标准 `TUNNEL`(MAVLink msg 385)承载打包载荷：显式 `payload_length` 免受 MAVLink v2 尾部零截断影响（告警行/日志条目合法含零字节），`payload[128]` 足够，`payload_type` 用于区分载荷类别。

`payload_type` 注册表（均落在 >32767 的「本地实验」段，符合 MAVLink 私有约定，不与公有 GCS 冲突）：

| payload_type | 含义 | 方向 |
|---|---|---|
| `0x8001` | 完整告警表（整表替换） | 目标设备 → 显示端 |
| `0x8002` | 消息日志增量 / LOGSEQ 心跳 | 目标设备 → 显示端 |

所有打包/解包为**纯函数对**，字节布局以本文为 TX/RX 唯一契约，两端不得各自猜测位定义。载荷一律**小端**。

# Part 1 完整告警表同步

## 3. 数据流

```text
本机 Px4Lite 告警 topic  Px4Lite_AlarmSnapshot_t.records[]
  └─ TX  MavTx_PackAlarmTable() → TUNNEL(0x8001) → LoRa
        └─ RX  MavlinkRx_UnpackAlarmTable() → RemoteTelemetry.alarm_records[]
              └─ App_GetDisplayAlarm(REMOTE) 填满 App_AlarmSnapshot_t.records[]
                    └─ display.c / display_lvgl  ← 已经过统一接口取数，UI 零改动
```

## 4. 告警表载荷布局（payload_type=0x8001）

| 字段 | 字节 | 说明 |
|---|---:|---|
| `ver` | 1 | 表内容版本，内容变化即自增 |
| `active_count` | 1 | 当前活动行数 N |
| 行[0..N-1] | 7×N | 见下 |

告警行(7 字节)：

| 字段 | 字节 | 来源 |
|---|---:|---|
| `source_id` | 1 | `Px4Lite_AlarmRecord_t.source_id`(低字节) |
| `fault_code` | 2 | `record.fault_code` |
| `severity` | 1 | `record.severity` |
| `active` | 1 | `record.active` |
| `age_s` | 2 | `(now_ms - record.raised_ms)/1000`，饱和到 u16 |

- 只发 **active 行**；`N ≤ PX4LITE_MODULE_COUNT`；payload = `2 + 7N`，满表也 ≪ 128B。
- payload_length = `2 + 7N`，N 可为 0（空表，表示当前无活动告警）。

## 5. 发送：on-change + 慢速保活

新增 TX 槽 `MAV_TX_SLOT_REMOTE_ALARM`（并入现有 13 槽轮转 `MavTx_Run`），槽内逻辑：

1. **内容变化检测**：对当前 active 行的 `source_id+fault_code+severity+active` 算一个轻量签名（如 FNV-1a 累加，不含 `age_s`，避免每秒抖动）。签名变化即 `ver++`，立即发一帧。
2. **慢速保活**：距上次发送 ≥ `PX4LITE_MAVLINK_REMOTE_ALARM_PERIOD_MS`(=2000) 也发一帧（即便无变化），供新接入/丢帧后恢复。
3. 不能用告警 topic 的 `header.sequence` 作变化判据——它每周期自增，会退化成每周期全发。

## 6. 接收与存储（RemoteTelemetry）

`Px4Lite_RemoteTelemetrySnapshot_t` 新增字段：

```c
Px4Lite_AlarmRecord_t alarm_records[PX4LITE_MODULE_COUNT]; /**< 远端活动告警行。 */
uint8_t  alarm_table_count;     /**< 远端活动告警行数。 */
uint8_t  alarm_table_ver;       /**< 远端告警表内容版本(载荷 ver)。 */
uint16_t reserved_alarmtbl;     /**< 对齐保留。 */
uint32_t alarm_table_update_ms; /**< 告警表最近更新时间，单位 ms。 */
```

- RX 收到 `0x8001`：**整表替换**（`ver` 变化即换；相同 `ver` 仅刷新时间戳），写 `alarm_records`/`alarm_table_count`，`Px4Lite_RemoteTelemetryCommit(..., PX4LITE_REMOTE_VALID_ALARM, now)` 复用既有 `VALID_ALARM` 位（摘要与整表同源）。
- 接收端把载荷的 7B 行还原到 `Px4Lite_AlarmRecord_t`：`age_s` 还原为 `raised_ms = now - age_s*1000`（近似），`updated_ms = now`。
- 断链：超过刷新窗口由 App 层判 `STALE`，保留最后一张表，不清零。

## 7. 显示层接线（只动 App 层一处）

`App_GetDisplayAlarm` 的 **REMOTE 分支**：从 `alarm_records[]` 填满 `App_AlarmSnapshot_t.records[]`（取代现在只填 highest 1 行），`active_count`/`highest_*` 一并归一。LOCAL 分支不变。`display.c` / `display_lvgl` 已通过 `App_GetDisplayAlarm` 取数 → UI 不改。

## 8. 测试（桌面单测）

- `MavTx_PackAlarmTable` / `MavlinkRx_UnpackAlarmTable` round-trip：空表、满表、含零字节行(severity=0/active=0)、`ver` 翻转。
- `App_GetDisplayAlarm`：REMOTE 返回完整多行、LOCAL 行为不变、超时返回 `STALE`、从未收返回 `NOT_READY`。

## 9. 带宽

常态 ~0 B/s（无告警变化）；5 行故障峰值 ~27 B/s；保活每 2s 一帧（空表 ~5 B/s）。叠加现有 ~483 B/s 仍 ≪ 550 预算。

# Part 2 消息日志同步

## 10. 现状与目标

现状：日志完全是 `display.c` 内部概念——`Display_UpdateMessageLog()` 用去抖机(`Display_LogDebounce`)对模块状态变化生成 `Display_LogMsg_t`(枚举，定义在 `display_text.h`，约 30 个值)，经 `Display_PagesPushLogMessage(msg, time)` 入显示内部环形缓冲；`App_GetDisplayMessageLog` 现返回 `NOT_READY`(占位)。

目标：把日志**生产者上提到业务层**，成为本机显示 / TX / 未来 PC 监控共用的结构化源；REMOTE 模式按目标设备日志增量同步。

## 11. 日志生产者上提到业务层

新增 `Business/Inc/app_message_log.h` + `Business/Src/app_message_log.c`：

- 持有 `App_DisplayLogEntry_t` 环形缓冲（容量 ≥ `APP_DISPLAY_LOG_CAP`），每条带**单调 `sequence`**。
- 把现 `display.c` 的去抖/状态变化→日志逻辑**迁移到此**（输入：`App_GetModuleStatus` 各模块状态、告警摘要、电池档位）；每周期推进，状态稳定 `DEBOUNCE_MS` 才提交一条。
- 对外：`App_GetDisplayMessageLog(LOCAL)` 直接返回本缓冲；TX 侧取 `sequence` 大于「已发」的新条目。
- `display.c` 不再生成日志，仅渲染。

**`message_id` 上提为协议枚举**：新增业务级 `App_LogMessageId_t`（镜像现 `Display_LogMsg_t` 取值，**append-only** 契约），`display_text.c` 改为按 `App_LogMessageId_t` 映射文字；`Display_LogMsg_t` 迁移/别名到它。理由：避免 Business 反依赖 `display_text.h`（层级倒挂），并使 `message_id` 成为稳定跨设备契约。

> 影响面：`display_text.h/.c`、`display_pages.c`、`display.c` 日志机移除。属本特性内的定向重构。

## 12. 日志载荷布局（payload_type=0x8002）

| 字段 | 字节 | 说明 |
|---|---:|---|
| `latest_seq` | 2 | 目标设备当前最新日志序号 |
| `count` | 1 | 本帧携带的条目数 M（0 = LOGSEQ 心跳） |
| 条目[0..M-1] | 8×M | 见下 |

日志条目(8 字节)：

| 字段 | 字节 | 说明 |
|---|---:|---|
| `sequence` | 2 | 条目序号，去重/增量依据 |
| `message_id` | 2 | `App_LogMessageId_t`，显示层映射文字 |
| `time_hhmmss` | 3 | 事件时间 HHMMSS 十进制整数(≤235959 < 2²⁴，小端 3 字节) |
| `severity` | 1 | 严重度（供告警关联/PC 监控） |

一帧最多约 `(128-3)/8 = 15` 条；屏幕同构最少只需 `sequence+message_id+time`，`severity` 供复用。

## 13. 发送：增量 + LOGSEQ 心跳

新增 TX 槽 `MAV_TX_SLOT_REMOTE_LOG`：

1. 有 `sequence` 大于「已发」的新条目时，按序打包（一帧装不下则下次续发），更新「已发」游标。
2. 无新条目且距上次发送 ≥ `PX4LITE_MAVLINK_REMOTE_LOG_PERIOD_MS`(=2000)：发 `count=0` 的 LOGSEQ 心跳（仅 `latest_seq`），告知对端当前最新序号。

## 14. 接收与存储（RemoteTelemetry）

`Px4Lite_RemoteTelemetrySnapshot_t` 新增日志环形缓冲：

```c
App_DisplayLogEntry_t log_entries[PX4LITE_REMOTE_LOG_CAP]; /**< 远端日志，按时间从旧到新。 */
uint16_t log_count;       /**< 有效条目数。 */
uint16_t log_last_seq;    /**< 已接收的最高日志序号。 */
uint32_t log_update_ms;   /**< 日志最近更新时间，单位 ms。 */
```

其中 `PX4LITE_REMOTE_LOG_CAP` = `APP_DISPLAY_LOG_CAP`(9)，与显示快照容量一致。

- RX 收到 `0x8002`：对每条 `sequence > log_last_seq` 的条目追加到环形缓冲并推进 `log_last_seq`；`sequence ≤ log_last_seq` 丢弃（去重）。**允许序号空洞**（丢帧不补传）。`count=0` 心跳仅用于让 `log_last_seq` 对齐 `latest_seq` 的认知，不补数据。
- 断链：超时 → App 层 `STALE`，保留最后日志。

## 15. 显示层接线

`App_GetDisplayMessageLog` 的 REMOTE 分支返回远端 `log_entries[]`（归一到 `App_DisplayLogSnapshot_t`，`version` 取 `log_last_seq`）；LOCAL 返回业务日志缓冲。`display.c` / `display_lvgl` 经 `App_GetDisplayMessageLog` 渲染，按 `message_id` 映射文字。

## 16. 测试（桌面单测）

- 日志打包/解包 round-trip；增量去重（重复 seq 丢弃、新 seq 追加、空洞容忍）；LOGSEQ 心跳不改数据。
- `App_GetDisplayMessageLog`：LOCAL 返回业务日志、REMOTE 返回远端日志、断链 `STALE`。
- 去抖机迁移后本机日志行为与迁移前一致（同输入产同序列）。

## 17. 带宽

增量活动期 ~15~30 B/s；LOGSEQ 心跳 @2s ~极小。与告警表叠加仍 < 550 预算；最坏（告警+日志同时爆发）用各自的 on-change/增量摊平峰值。

# 18. 实施顺序

**Part 1（告警表，先做）**

1. 定义 TUNNEL 0x8001 打包/解包纯函数 + 告警行布局常量。
2. RemoteTelemetry 增告警行字段；RX 接 0x8001 整表替换。
3. TX 增 `MAV_TX_SLOT_REMOTE_ALARM`（内容签名 on-change + 保活）。
4. `App_GetDisplayAlarm` REMOTE 填满 records。
5. 桌面单测（§8）。

**Part 2（消息日志，随后）**

6. 新增 `App_LogMessageId_t`（协议枚举），`display_text` 改按它映射；迁移 `Display_LogMsg_t`。
7. 新增 `Business/app_message_log`，迁入去抖/生成逻辑；`display.c` 移除日志机、改渲染。
8. `App_GetDisplayMessageLog(LOCAL)` 返回业务日志。
9. TUNNEL 0x8002 打包/解包；RemoteTelemetry 增日志缓冲；RX 增量去重。
10. TX 增 `MAV_TX_SLOT_REMOTE_LOG`（增量 + LOGSEQ 心跳）。
11. `App_GetDisplayMessageLog(REMOTE)` 返回远端日志。
12. 桌面单测（§16）。

**收尾**：Keil Rebuild All，目标 `0 Error(s), 0 Warning(s)`。

# 19. 验收标准

| 验收项 | 通过条件 |
|---|---|
| 告警页（REMOTE） | 显示目标设备完整活动告警列表（多行），非仅最高 1 行。 |

| 传码不传文字 | 链路仅传枚举/故障码；提示文字两端各自映射；消息枚举为 append-only 协议契约。 |
