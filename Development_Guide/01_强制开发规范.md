# STM32F407 统一驱动与数据完整性强制开发规范

## 1. 适用范围

本规范适用于：

- GNSS、IMU、气压计、电源等传感器
- LoRa、5G、CAN、UART 等通信模块
- SD 卡日志
- 控制与报警模块
- 后续 A 核/Linux 数据交互

本文中的“必须”“禁止”均为代码评审门禁。

## 2. 核心原则

1. 禁止通过盲目扩大任务栈或 FreeRTOS 堆掩盖设计问题。
2. 驱动只负责硬件、原始数据和设备状态，不承载业务策略。
3. 任务不得直接读取另一个模块的内部变量或 DMA 缓冲区。
4. 数据必须完整生成后一次发布，禁止边写边给读者使用。
5. 发送成功必须表示完整帧已经交付，不能只表示“开始发送”。
6. ISR 只搬运、记录位置或发通知，禁止解析、格式化输出和阻塞。
7. 所有跨任务数据必须有所有权、长度、序号、时间戳和有效标志。

## 3. 内存与任务强制规范

### 3.1 禁止事项

- 禁止一个传感器创建一个永久任务。
- 禁止在任务栈中定义大数组、完整通信帧或 SD 扇区缓存。
- 禁止在周期任务中使用递归、可变长数组和无界格式化输出。
- 禁止在运行期间频繁 `pvPortMalloc()` / `vPortFree()`。
- 禁止因为栈溢出直接把所有任务栈翻倍。
- 禁止用同一块全局缓冲区同时执行采集、解析和发送。

### 3.2 允许的内存模型

| 数据类型 | 强制模型 |
|---|---|
| GNSS、气压、电源、状态 | Latest Snapshot |
| IMU 等高频连续采样 | 固定长度 FIFO |
| 报警、命令、确认 | FreeRTOS Queue |
| LoRa/5G/SD 大帧 | 固定块 Memory Pool |
| DMA 接收 | 专属 DMA 缓冲区 |

### 3.3 栈使用规则

- 任务函数局部变量应以标量和小结构体为主。
- 超过 128 字节的局部对象必须在评审中说明。
- 超过 256 字节的缓冲区必须改为静态专属缓冲区或内存池。
- 发布后的大数据只传递块索引或指针，不复制整块。
- 每个任务必须定期记录 `uxTaskGetStackHighWaterMark()`。
- 最低剩余栈必须大于配置栈的 25%，且不得低于 100 word。
- 栈不足时先减少局部对象、调用深度和格式化输出，再评估调整。

### 3.4 堆使用规则

- 正式运行阶段只允许系统启动时创建任务、队列、互斥量。
- 初始化完成后原则上禁止动态申请。
- FreeRTOS 堆峰值使用率不得超过 75%。
- 新增任务必须提交栈预算、优先级、周期和最坏执行时间。
- 功能关闭时不得创建对应任务、队列或大缓冲区。

## 4. 驱动模板强制规范

每个设备必须提供以下职责：

```c
Result_t Device_Init(void);
Result_t Device_Service(uint32_t now_ms);
Result_t Device_CopySnapshot(Device_Snapshot_t *out);
Result_t Device_GetStatus(Component_Status_t *out);
```

约束：

- `Init()` 只初始化该设备拥有的资源。
- `Service()` 由统一采集任务调用，不得永久阻塞。
- `CopySnapshot()` 只复制已经发布的完整数据。
- `GetStatus()` 不得主动访问慢速总线。
- 驱动内部必须区分：未初始化、启动中、在线、降级、离线、失败。
- 驱动必须维护 `last_rx_ms`、`last_valid_ms`、错误计数和丢包计数。

## 5. 防止读取半段数据

### 5.1 Latest Snapshot

禁止直接共享一个正在写入的结构体。发布必须使用以下任一方案：

#### 方案 A：短临界区复制

适用于较小、低频结构体。

```c
void Topic_Publish(const Topic_t *source)
{
    taskENTER_CRITICAL();
    g_topic = *source;
    g_topic_ready = 1U;
    taskEXIT_CRITICAL();
}

Result_t Topic_Copy(Topic_t *destination)
{
    taskENTER_CRITICAL();
    if (g_topic_ready == 0U)
    {
        taskEXIT_CRITICAL();
        return RESULT_NOT_READY;
    }

    *destination = g_topic;
    taskEXIT_CRITICAL();
    return RESULT_OK;
}
```

临界区内禁止解析、计算、打印和访问外设。

#### 方案 B：双缓冲加发布索引

适用于结构较大或发布频率较高的数据。

1. 写者只写非活动缓冲区。
2. 所有字段写完后更新 `sequence`、时间戳和 CRC。
3. 执行内存屏障。
4. 最后一次性切换活动索引。
5. 读者先读取活动索引，再复制该缓冲区。

写者不得修改当前活动缓冲区。

### 5.2 序号一致性

不方便加锁的平台交互必须使用奇偶序号：

```text
开始写入：sequence 变为奇数
写入数据：更新全部字段
完成写入：sequence 变为下一个偶数
```

读者执行：

```text
读取 sequence1
sequence1 为奇数则重试
复制数据
读取 sequence2
sequence1 != sequence2 则丢弃并重试
```

该方法适用于 MCU 与 Linux 共享内存，但仍必须处理缓存一致性。

## 6. DMA 与字节流接收规范

1. DMA 缓冲区只归 BSP 接收器所有。
2. 解析器不得保存 DMA 缓冲区内部指针供以后使用。
3. ISR 只更新写入位置、错误标志或发送任务通知。
4. 消费者必须使用独立读位置，按已确认长度取数据。
5. 写位置和读位置必须使用无符号回绕计算。
6. 缓冲区满时必须明确采用“丢最旧”或“拒绝新数据”策略。
7. 溢出必须累计 `drop_count`，禁止静默覆盖。
8. UART 错误恢复必须重启 DMA，并清理软件读写状态。
9. 进入临界区前保存 PRIMASK，退出时恢复原状态。
10. 禁止无条件 `__enable_irq()`，避免破坏调用者的中断状态。

## 7. 防止解析半包

所有流式协议都必须经过以下状态：

```text
SEARCH_HEADER -> RECEIVE_BODY -> RECEIVE_CHECK -> FRAME_COMPLETE
```

只有满足以下条件才允许交给上层：

- 帧头正确
- 声明长度在允许范围内
- 实际接收长度等于声明长度
- CRC/校验和正确
- 协议版本支持
- 消息类型合法

不满足时必须丢弃整帧，禁止用“已经收到的部分字段”更新快照。

NMEA 必须等到完整 `\r\n` 或完整校验字段后解析。校验失败的语句不得
刷新 `last_valid_ms`。

## 8. 发布数据规范

每个正式测量值必须包含：

```c
typedef struct
{
    uint16_t device_id;
    uint16_t flags;
    uint32_t sequence;
    uint32_t sample_time_ms;
    uint32_t publish_time_ms;
    uint8_t valid;
    uint8_t quality;
    uint16_t reserved;
} Measurement_Header_t;
```

强制语义：

- `sample_time_ms`：物理采样发生时间。
- `publish_time_ms`：完成运算并发布的时间。
- `sequence`：每次完整发布后递增。
- `valid`：当前值是否可用于业务。
- `quality`：数据质量，不等同于通信在线。
- `flags`：校准、饱和、估算、陈旧等标志。

发布顺序必须是：

```text
采集完整原始数据
-> 校验
-> 单位转换
-> 校准/过滤
-> 计算质量
-> 填充完整临时结构
-> 一次性发布
```

## 9. 防止传输半段数据

### 9.1 发送帧格式

所有 LoRa、5G、CAN 分包和 Linux 链路必须包含：

```text
Magic
Protocol Version
Message Type
Payload Length
Sequence
Timestamp
Payload
CRC
```

禁止直接发送 C 结构体内存，避免填充、字节序和版本问题。

### 9.2 发送缓冲区所有权

发送接口必须满足以下一种语义：

1. 同步发送：返回前已经完整发送。
2. 异步复制：驱动在返回前已复制完整帧。
3. 异步零拷贝：发送完成回调前，调用者不得修改或释放缓冲块。

接口必须明确采用哪一种，禁止含糊。

### 9.3 部分发送处理

底层返回已发送长度时，上层必须循环处理剩余部分：

```text
offset = 0
while offset < frame_length:
    sent = transport_send(frame + offset, frame_length - offset)
    sent > 0      -> offset += sent
    busy          -> 等待通知后重试
    timeout/error -> 整帧失败，不得标记成功
```

只有 `offset == frame_length` 才能更新“发送成功序号”。

### 9.4 接收与重组

- 分包必须包含消息序号、总分片数、当前分片号和总长度。
- 接收端必须确认所有分片到齐后再校验整包 CRC。
- 超时、重复、越界或缺片时丢弃整包。
- 不得把已经到达的部分分片发布为完整业务数据。

### 9.5 端到端确认

关键命令、参数配置和控制消息必须有 ACK：

```text
command_sequence + command_id + result + receiver_state
```

没有 ACK 只能表示链路层可能已发送，不能表示业务执行成功。

## 10. SD 日志完整性规范

- 日志使用固定块内存池，不在任务栈中创建 512/1024 字节缓存。
- 生产者提交完整记录，日志任务独占 FatFs/SD。
- 每条记录包含长度、序号、时间戳和 CRC。
- SD 写入失败不得阻塞高优先级采集任务。
- 缓冲池满时按策略丢弃，并累计日志丢弃数。
- 掉电安全采用周期同步和完整记录边界，禁止写半条记录后标记成功。

## 11. 状态、报警与恢复规范

状态必须区分：

| 状态 | 含义 |
|---|---|
| UNINITIALIZED | 尚未初始化 |
| STARTING | 初始化完成，等待首个有效数据 |
| ONLINE | 通信和数据均正常 |
| DEGRADED | 有通信但数据质量不足 |
| OFFLINE | 超过超时阈值无新数据 |
| FAILED | 初始化失败或不可恢复故障 |

通信在线和数据有效必须分开。例如 GNSS 有 NMEA 但无定位，应为
`DEGRADED`，不是 `OFFLINE`。

报警事件必须包含来源、故障码、等级、激活/恢复、时间戳和详情。
同一故障禁止每周期重复入队，必须进行边沿检测和去抖。

## 12. 调试规范

- 原始数据打印只能由专用调试宏开启。
- 正式耐久测试禁止逐字节、逐帧打印。
- 周期调试输出不得快于 1 Hz，除非专项测试有明确要求。
- 调试关闭后不得改变采集、解析、状态机和发布逻辑。
- `DEBUG_ENABLE` 只控制调试基础设施；周期状态输出必须再使用
  `DEBUG_PERIODIC_ENABLE`，原始流输出必须使用独立的 RAW 宏。
- 不得在 ISR 内调用 `printf`。

必须提供以下运行指标：

- 每个任务最小剩余栈
- FreeRTOS 最小剩余堆
- FIFO 峰值与溢出数
- DMA/协议丢包数
- CRC 错误数
- 模块最后接收和最后有效时间

## 13. 代码评审门禁

新增模块合入前必须回答：

1. 谁拥有接收缓冲区？
2. 谁可以写，谁可以读？
3. 如何保证读不到写到一半的数据？
4. 如何识别完整帧？
5. 如何处理部分发送？
6. 发送完成的定义是什么？
7. 超时和恢复策略是什么？
8. 数据失效后旧值如何处理？
9. 最坏栈、堆、FIFO 和执行时间是多少？
10. 功能关闭时释放了哪些任务和内存？

任一问题无法回答，不得合入。

## 13.1 时间单位强制规则

- 名称以 `_ms` 结尾的字段必须存储真实毫秒值。
- 名称以 `_ticks` 结尾的字段才允许存储 RTOS Tick。
- 禁止把 `xTaskGetTickCount()` 直接写入 `_ms` 字段。
- 公共框架统一通过 `PlatformGetMs()` 获取毫秒时间。
- 若 Tick 频率不是 1000 Hz，必须显式转换。
- 周期任务必须使用 `vTaskDelayUntil()`，避免长期累计漂移。
- `vTaskDelay()` 只允许用于退避、重试或无周期要求的流程。
- 微秒接口必须具有真实的亚毫秒分辨率；禁止用 `ms * 1000`
  冒充微秒时钟。
- 微秒时间戳允许自然回绕，所有时间差必须使用无符号减法。

## 13.2 通信缓冲区所有权强制规则

- 文件作用域发送缓冲区必须在声明处标注唯一拥有任务。
- 异步发送完成前，拥有任务不得再次编码覆盖该缓冲区。
- 多个生产者需要发送缓冲区时，必须改用固定内存池。
- 禁止用“当前只有一个调用者”代替明确的所有权设计。

## 13.3 报警输出强制规则

- 蜂鸣器和指示灯由全部活动报警中的最高等级决定。
- 低等级事件不得关闭仍然活动的高等级报警。
- 报警恢复必须通过 `source_id + fault_code` 精确匹配。
- 活动报警表满时必须计数并上报，禁止静默丢弃。

## 13.4 看门狗强制规则

- 禁止 Health 任务无条件喂狗。
- 所有必需任务必须在完成本周期主要工作后更新心跳。
- 只有必需任务全部出现且未超时，才允许刷新硬件看门狗。
- 看门狗刷新必须封装在平台层，业务任务不得直接访问 IWDG。
- 启用硬件看门狗但未实现 BSP 刷新函数时，构建必须失败。

## 13.5 状态机归属规则

- 驱动层只表达硬件事实、原始数据质量和最近接收信息。
- Offline、Failed、恢复和系统降级由 Health 层统一判定。
- 公开组件状态按转移类别单一归属：数据路径（采集/通信任务）只写正向状态
  ONLINE/DEGRADED（基于本周期是否取得合格数据）；Health 独占 OFFLINE、FAILED、
  恢复与系统降级（基于超时与判定）。同一类转移不得有第二个写入者。
- 驱动和 Health 不得各自维护不同超时阈值的公开状态机。
- 新数据检测使用独立 `sequence`，禁止用时间戳是否变化代替序号。

## 14. 必测项目

- DMA 缓冲区回绕
- 接收半帧、粘包、乱序和 CRC 错误
- 发送接口只发送部分字节
- 任务切换发生在结构体复制中间
- 队列、FIFO、内存池满
- 传感器拔出、恢复和反复抖动
- GNSS 有数据无定位与完全失联
- SD 卡拔出和写入超时
- LoRa/5G 断链重连
- 长时间调试关闭运行
- 每个任务最小剩余栈和堆最低水位

通过异常注入和至少 24 小时运行测试后，模块才可标记为正式版本。
