# 5G 与 RemoteID 架构方案

版本：2026-06-26  
状态：架构方案，不代表代码已完成  
适用工程：Formal Framework / STM32F407 + HAL + FreeRTOS + Keil MDK-ARM

## 1. 结论

当前工程已经形成较清晰的分层边界，后续 5G、树莓派以太网控制、ESP32 RemoteID 都建议沿用现有架构接入，不另起一套控制链路。

核心方案如下：

1. STM32 继续作为外设控制和状态判定的权威节点。
2. 5G 模块只作为通信能力扩展，控制面由 STM32 通过 AT 指令管理。
3. 树莓派作为网络网关和上位应用节点，通过 5G 入网，通过以太网向 STM32 发送受控命令。
4. 所有外部命令统一进入 `Framework/Src/px4lite_command.c`，不允许网络、5G、显示、RemoteID 代码直接控制外设。
5. RemoteID 使用 ESP32 承担广播任务，STM32 只提供小型身份与位置快照，ESP32 按 OpenDroneID / ASTM Remote ID 语义组织广播。
6. 后续扩展必须保持栈占用不扩大：固定长度帧、静态缓冲、分步解析、无大 JSON、无周期任务大结构体栈上拷贝。

## 2. 当前工程架构基线

工程当前采用单向依赖：

```text
Core -> Business -> Framework -> Platform Adapter -> Driver -> BSP -> HAL
```

各层职责保持如下：

| 层级 | 当前职责 | 后续扩展要求 |
|---|---|---|
| Core | 启动、HAL 初始化、FreeRTOS 启动、中断入口 | 只做组合根，不承载协议和业务 |
| Business | 业务流程、显示业务入口、应用数据 API | 只能通过 `app_data_api.h` 读数据 |
| Framework | topic、registry、health、recovery、command、调度 | 统一承接命令、状态、恢复、告警 |
| Platform Adapter | Driver/BSP 到 Framework 的类型转换 | 仍由 `px4lite_platform_f407.c` 收口 |
| Driver | 芯片协议、通信协议、解析、状态机 | 5G、RemoteID、网络控制协议放这里 |
| BSP | GPIO、UART、SPI、ETH、DMA、IRQ、原始收发 | 不做协议解析和业务判断 |
| HAL | STM32 HAL 底层 | 不写项目业务 |

关键边界：

- Business / Display 不直接读 BSP、Sensor、Driver 私有变量。
- Display 不直接包含 Framework 模块枚举和故障头文件。
- 通信发送不能直接发送 C struct 内存，必须逐字段编码。
- Driver 只记录硬件事实和通信事实，OFFLINE / FAILED 由 Health 统一判定。
- 命令执行统一在 Command 执行器，不散落到 RX、TX、BSP 或 Display。

## 3. 后续总体拓扑

建议后续系统拓扑：

```text
远端平台 / 网络中其他设备
        |
      5G 网络
        |
  5G 模块 USB 数据口
        |
     树莓派
        |
      Ethernet
        |
     STM32F407
        |
  Framework Command 执行器
        |
 各外设 service / driver / control
```

RemoteID 独立广播拓扑：

```text
STM32F407
  |  小型 RemoteID 快照帧
  |  UART / SPI / 其他轻量链路
  v
ESP32 RemoteID 模块
  |  OpenDroneID / ASTM Remote ID 语义字段
  v
BLE / Wi-Fi 广播
```

这样划分后，5G 网络、树莓派、RemoteID 都不会破坏 STM32 内部边界。

## 4. 5G 模块接入方案

5G 模块分成两个面：

| 面 | 所属设备 | 职责 |
|---|---|---|
| 控制面 | STM32 | AT 指令、模块上电、附着查询、状态确认、恢复配置 |
| 数据面 | 树莓派 | USB 网络口、业务网络通信、远端平台交互 |

STM32 对 5G 的定位：

- 只管理 5G 模块是否正常、是否附着网络、是否需要恢复。
- 不在 STM32 上承载复杂 TCP/HTTP/MQTT/JSON 业务。
- 不把原始 AT 命令暴露给 Business 或 Display。
- 5G 状态进入模块状态和 Health，必要时通过 App API 展示。

推荐目录：

| 目录 / 文件 | 作用 |
|---|---|
| `Bsp/Inc` / `Bsp/Src` | 5G 模块 UART、PWRKEY、RESET、STATUS 引脚、DMA/IRQ 原始收发 |
| `Driver/Comm/Inc` / `Driver/Comm/Src` | 5G AT 状态机、响应解析、连接事实、恢复请求 |
| `Framework/Src/px4lite_platform_f407.c` | 5G Driver 状态转换为 Framework 模块状态 |
| `Framework/Src/px4lite_health.c` | 5G 超时、降级、恢复判定 |
| `Business/Inc/app_data_api.h` | 对显示或业务提供状态读取接口 |

## 5. 树莓派以太网控制方案

树莓派通过 5G 入网，再通过以太网给 STM32 发命令。STM32 不能把树莓派视为“可信直接外设控制器”，而应视为一个外部命令来源。

命令链路：

```text
树莓派网络应用
  -> Ethernet frame / UDP / TCP 小型命令帧
  -> STM32 Ethernet BSP
  -> Driver/Comm/net_control 协议解析
  -> Framework/Src/px4lite_command.c
  -> 目标模块 service 执行
  -> COMMAND_ACK / 自定义 ACK 返回
```

控制原则：

1. 树莓派只发命令，不直接改 STM32 内部状态。
2. STM32 负责校验权限、目标、状态、安全条件和执行结果。
3. 外部命令必须有 `seq`、`command_id`、`target_node`、`remote_id`、`payload_len`、`crc`。
4. 不支持的命令必须明确 ACK 为 unsupported，不能静默丢弃。
5. 高风险命令要有状态门控，例如急停、外设复位、模式切换。

建议第一阶段使用固定二进制小帧，不建议一开始上 JSON：

```text
magic/version/seq/source_id/target_id/command_id/payload_len/payload/crc16
```

这样对 STM32 栈和堆最友好，也便于丢包、重传和 ACK。

## 6. RemoteID 使用 ESP32 的方案

RemoteID 建议由 ESP32 单独承担广播。STM32 只提供身份、位置、速度、时间和状态快照，不直接生成 BLE/Wi-Fi 广播细节。

采用这种划分的原因：

- ESP32 原生适合 BLE / Wi-Fi 广播。
- STM32F407 避免增加复杂无线协议栈。
- RemoteID 后续格式变更时，主要改 ESP32 固件，不冲击飞控主框架。
- STM32 仍保留身份来源和飞行状态的权威性。

RemoteID 建议对齐的商用语义：

| 参考体系 | 用途 |
|---|---|
| ASTM F3411 Remote ID | Remote ID 和跟踪的主流标准语义 |
| OpenDroneID | 开源实现和 MAVLink 消息体系常用字段 |
| IETF DRIP | 后续身份可信、网络身份和注册体系扩展参考 |

STM32 发给 ESP32 的快照建议保持小而固定：

| 字段 | 说明 |
|---|---|
| `node_id` | 本机节点 ID，继续沿用 `PX4LITE_NODE_ID` |
| `system_id` | MAVLink system id，继续按 `node_id + 1` |
| `uas_id` | 飞行器 / 设备身份，固定最大长度 |
| `operator_id` | 操作者或单位身份，固定最大长度 |
| `lat_deg_e7` / `lon_deg_e7` | 经纬度，整数缩放 |
| `alt_mm` | 高度，毫米 |
| `heading_cdeg` | 航向，0.01 度 |
| `speed_cms` | 水平速度，cm/s |
| `timestamp_ms` | STM32 当前时间戳 |
| `status` | 飞行 / 定位 / 广播状态 |

RemoteID 不改变现有 LoRa 远端槽位和 MAVLink `system_id` 规则：

- LoRa 仍用节点槽位和 `system_id` 区分主从。
- RemoteID 是“身份展示和对外广播身份”，不是 LoRa 节点编号替代品。
- Display 后续如要展示 RemoteID，只替换身份字段来源，不改远端快照结构。

## 7. 命令统一收口

后续新增的命令入口都必须收口到：

```text
Framework/Src/px4lite_command.c
```

统一入口包括：

| 来源 | 是否允许直接控制外设 | 正确路径 |
|---|---|---|
| MAVLink COMMAND_LONG | 否 | MAVLink RX -> Command 执行器 |
| 树莓派以太网命令 | 否 | net_control -> Command 执行器 |
| 5G 网络远端命令 | 否 | 树莓派 -> Ethernet -> Command 执行器 |
| Display 触摸命令 | 否 | Display/App facade -> Command 或业务入口 |
| RemoteID | 否 | 只上报身份广播状态，不控制外设 |

这样后续加 5G、RemoteID、Remote Control、外设复位等能力时，权限校验和 ACK 语义只有一个地方维护。

## 8. 栈和内存控制要求

后续 5G、以太网、RemoteID 开发必须遵守以下约束：

1. 不在周期任务栈上放完整系统快照、完整告警表、大 payload、大 JSON。
2. RX 解析使用文件级 `static` 状态机和固定缓冲。
3. 大 payload 必须使用静态块、固定队列或分片缓冲。
4. comm / display / health 任务内只拷贝小型 summary。
5. ISR 只更新计数、写位置或发任务通知，不解析协议、不打印、不执行恢复。
6. 不为每个普通外设单独创建高优先级任务。
7. 5G AT、以太网命令、RemoteID 快照都挂入现有 `comm` 或对应 service work，确有必要新建任务时必须给出栈预算和实测水位。
8. 启动后不动态分配内存，避免长期运行碎片和不可预测失败。

建议控制策略：

| 模块 | 数据结构策略 |
|---|---|
| 5G AT | 小型行缓冲 + 状态机 + 超时计数 |
| Ethernet command | 固定帧头 + 固定最大 payload + CRC |
| RemoteID STM32->ESP32 | 固定快照结构逐字段编码 |
| Display | 只读 App 显示快照，不复制大表 |
| Debug | 输出 summary，不在栈上拼大文本 |

## 9. 落地阶段规划

第一阶段：架构固化

- 明确 5G、以太网控制、RemoteID 的目录归属。
- 定义命令帧、ACK、权限和错误码。
- 定义 RemoteID 快照字段和 ESP32 通信帧。
- 更新接入指南、完成度清单和变更记录。

第二阶段：5G 控制面

- BSP 完成 5G UART / PWRKEY / RESET / STATUS。
- Driver 完成 AT 状态机、附着查询、恢复请求。
- Framework 接入模块注册、Health、恢复和状态上报。
- Display 只显示 5G 模块状态，不显示原始 AT。

第三阶段：树莓派以太网控制

- 定义树莓派到 STM32 的小型命令帧。
- STM32 完成 net_control Driver。
- 所有命令进入 `px4lite_command.c`。
- 加入 ACK、超时、重复 seq 去重和安全门控。

第四阶段：ESP32 RemoteID

- STM32 输出 RemoteID 小型快照。
- ESP32 固件实现 OpenDroneID / ASTM Remote ID 语义广播。
- STM32 只监控 ESP32 在线、广播状态和错误计数。
- Display 可展示身份字段和广播状态。

第五阶段：联调和发布门禁

- Keil Rebuild All 达到 `0 Error(s), 0 Warning(s)`。
- 记录任务栈水位，确认未扩大关键任务栈风险。
- 长稳测试 5G 在线、树莓派命令、RemoteID 广播、LoRa 收发互不影响。
- 完成 `Development_Guide/` 和 `Change_History/` 同步。

## 10. 风险与控制措施

| 风险 | 控制措施 |
|---|---|
| 树莓派和 STM32 同时控制 5G 模块 | 明确 STM32 管控制面，树莓派走 USB 数据面 |
| 网络命令绕过 STM32 安全逻辑 | 所有命令进入 Command 执行器 |
| RemoteID 影响主控实时性 | ESP32 承担广播，STM32 只发小快照 |
| STM32 栈被协议解析撑大 | 固定帧、静态缓冲、分步解析 |
| Display 或 Business 破坏分层 | 继续通过 `app_data_api.h` 读取 |
| 监管格式变化 | ESP32 固件适配广播格式，STM32 快照语义保持稳定 |
| 5G 数据业务过重 | 复杂网络业务放树莓派，不放 STM32 |

## 11. 当前

本工程后续扩展 5G 和 RemoteID 不需要推翻当前架构。建议保持 STM32 为主控和外设权威，树莓派负责网络应用，5G 模块负责入网能力，ESP32 负责 RemoteID 广播能力。所有外部命令统一收口到 Framework Command 执行器，所有外设状态统一进入 Health 和 App API。这样既能支持后续 5G 网络交互、RemoteID 身份广播，也能保持现有 FreeRTOS 栈、分层边界和长期维护成本可控。
