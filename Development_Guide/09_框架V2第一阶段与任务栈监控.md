# 框架 V2 第一阶段与任务栈监控

## 1. 目标平台

当前正式目标为 `STM32F407ZGT6`：

- Cortex-M4F。
- 1 MB Flash。
- 128 KB 普通 SRAM，起始地址 `0x20000000`。
- 64 KB CCM RAM，起始地址 `0x10000000`。
- LQFP144 封装。

注意：

- DMA 不能访问 CCM RAM。
- DMA 缓冲、外设收发缓冲和需要 DMA 访问的数据必须放在普通 SRAM。
- CCM 只适合后续明确放置的算法临时数据、非 DMA 栈或计算缓存。
- 当前 FreeRTOS heap、任务栈和 GNSS DMA 缓冲均位于普通 SRAM。
- 未经链接脚本和内存评审，不得自行把变量放入 CCM。

## 2. 本次完善内容

### 2.1 Module Registry 与 Lifecycle

新增：

```text
Framework/Inc/px4lite_registry.h
Framework/Src/px4lite_registry.c
```

模块生命周期：

```text
REGISTERED
 -> INITIALIZING
 -> SELF_CHECK
 -> STARTING
 -> RUNNING
 -> RECOVERING
 -> STOPPED / FAILED / DISABLED
```

当前先注册：

- GNSS
- Estimator

这一步只建立通用机制，不增加新的设备功能。后续模块通过 descriptor
注册，不再把初始化调用散落到任务入口。

### 2.2 Work Item 周期调度

新增：

```text
Framework/Inc/px4lite_work.h
Framework/Src/px4lite_work.c
```

当前 Sensor、Estimator、Health 任务仍然保留，但任务内正式工作改为
`Px4Lite_WorkItem_t` 调度：

```text
固定 FreeRTOS Task
    -> WorkRunDue()
        -> 到期判断
        -> 模块 Run()
        -> 执行次数
        -> deadline miss
        -> 最大执行时间
```

后续增加同类传感器时，应优先增加 Work Item，而不是增加一个永久任务。

### 2.3 任务栈与 heap 串口监控

新增：

```text
Debug/Inc/debug_task_monitor.h
Debug/Src/debug_task_monitor.c
```

监控对象：

- `sensor`
- `estimator`
- `health`
- `biz_system`
- `biz_acq`
- `biz_display`

监控内容：

- 配置栈大小，单位 word。
- 历史峰值栈使用量。
- 历史最低剩余栈，单位 word 和 byte。
- 当前剩余 FreeRTOS heap。
- 历史最低剩余 heap。
- 历史峰值 heap 使用量。

## 3. 启用和关闭

配置文件：

```text
Debug/Inc/debug_config.h
```

启用：

```c
#define DEBUG_TASK_STACK_ENABLE
```

关闭时只注释这一行：

```c
/* #define DEBUG_TASK_STACK_ENABLE */
```

串口报告周期：

```c
#define DEBUG_TASK_STACK_REPORT_PERIOD_MS  5000U
```

该开关只控制栈和 heap 统计输出。关闭后不会改变 GNSS 接收、解析、Topic
发布、任务周期和业务逻辑。

## 4. 串口输出示例

```text
[DBG] MEM: heap_cfg=40960 heap_free=28672 heap_min=28160 heap_peak_used=12800
[DBG] STACK: task=sensor cfg=384W peak=164W min_free=220W/880B OK
[DBG] STACK: task=estimator cfg=384W peak=132W min_free=252W/1008B OK
[DBG] STACK: task=health cfg=384W peak=180W min_free=204W/816B OK
[DBG] STACK: task=biz_system cfg=256W peak=96W min_free=160W/640B OK
[DBG] STACK: task=biz_acq cfg=384W peak=148W min_free=236W/944B OK
[DBG] STACK: task=biz_display cfg=384W peak=120W min_free=264W/1056B OK
```

解释：

- `cfg=384W`：创建任务时配置 384 word。
- F407 的 `StackType_t` 为 32 bit，因此 384 word 等于 1536 byte。
- `min_free`：任务运行以来曾经出现过的最小剩余栈。
- `peak`：根据配置栈减去最低剩余栈计算出的历史峰值使用量。
- `heap_min`：系统运行以来 FreeRTOS heap 的最低剩余量。
- `heap_peak_used`：历史最大 heap 使用量。

## 5. 判断规则

当前调试器在以下任一条件满足时输出 `WARN`：

- 最低剩余栈小于 100 word。
- 最低剩余栈小于配置栈的 25%。

建议：

| 结果 | 处理 |
|---|---|
| 剩余大于 35% | 余量充分 |
| 剩余 25% 至 35% | 继续长时间测试 |
| 剩余低于 25% | 分析局部变量、调用深度和格式化输出 |
| 剩余低于 100 word | 不允许发布 |
| 触发 StackOverflowHook | 立即按严重故障处理 |

不能只运行几分钟就缩小任务栈。至少覆盖：

- GNSS 有定位和无定位。
- Display 刷新和触摸。
- 队列接近满载。
- 调试打印开启和关闭。
- 通信和日志后续接入后的峰值路径。
- 24/72 小时稳定性测试。

第一次实测发现 Sensor 仅剩 32 word、Business System 仅剩 90 word。
根因和定向处理记录见：

```text
Change_History/2026-06-11_14_任务栈实测与定向优化.md
```

处理原则是先移除正式链路中无用的大局部对象，再根据实测结果只调整
确实不足的任务栈，不统一扩大所有任务。

## 7. 当前框架阶段

本次完成后，框架由“固定任务直接调用模块函数”升级为：

```text
固定任务
 -> Work Item 调度
 -> Module Registry / Lifecycle
 -> 模块服务函数
 -> Topic / FIFO / Event
 -> Domain / Business API
```

当前 Registry 和 Work Item 是第一版基础机制。后续仍需补充：

- Health Check 注册表。
- Alarm Manager。
- Recovery Policy 和自动恢复调度。
- Work Item 统计进入 SystemHealth。
- 模块依赖、必选/可选和启动顺序。
- 参数、性能计数和 Crash Record。
