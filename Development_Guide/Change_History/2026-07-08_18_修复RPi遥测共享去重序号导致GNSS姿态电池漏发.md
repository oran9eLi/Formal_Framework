# 2026-07-08_18_修复RPi遥测共享去重序号导致GNSS姿态电池漏发(回归)

## 现象

RPi 侧收不到 GNSS 信息(以及姿态、主电池)。其余遥测正常。

## 根因(2026-07-08_15 的回归)

`2026-07-08_15` 让 RPi 标准遥测独立于 LoRa:同一批编码器被 LoRa、RPi 两趟复用,凡"按发送成功推进"的状态需按发送目标 `s_send_target` 拆成两份。当时**只拆了电机分片游标、模块状态分片、电池电流去重序号**,**漏了另外四个按 topic sequence 去重的编码器**——它们的去重序号仍放在共享的 `Px4Lite_MavlinkTxStats_t`(`s_stats`)里:

- `s_stats.last_gps_sequence`(GPS_RAW)
- `s_stats.last_detail_sequence`(GNSS_DETAIL / GNSS_SAT)
- `s_stats.last_attitude_sequence`(ATTITUDE)
- `s_stats.last_battery_sequence`(BATTERY)

`Px4Lite_CommWorkRun` 里 **LoRa 趟(`Px4Lite_MavlinkTxRun`)先跑**,消费掉当前采样并把共享序号更新为该 sample 的 sequence;随后 RPi 趟(`Px4Lite_MavlinkTxRunRpi`)对同一 sample 编码时 `header.sequence == s_stats.last_*_sequence` 成立 → 返回 `IDLE` 跳过。结果这四类帧被 LoRa 趟"独占",**RPi 趟永远漏发**。

## 修复

把这四个去重序号改成按目标分离的模块级数组 `[MAV_TX_TARGET_COUNT]`(与电池电流一致),编码器按 `s_send_target` 索引:

```c
static uint32_t s_last_gps_sequence[MAV_TX_TARGET_COUNT];
static uint32_t s_last_detail_sequence[MAV_TX_TARGET_COUNT];
static uint32_t s_last_attitude_sequence[MAV_TX_TARGET_COUNT];
static uint32_t s_last_battery_sequence[MAV_TX_TARGET_COUNT];
```

- 四对编码器读写点改用 `s_last_*_sequence[s_send_target]`;Init 增设 memset 复位。
- 从 `Px4Lite_MavlinkTxStats_t` 删掉这四个字段 + 已随 SCALED_PRESSURE 作废的 `last_pressure_sequence`(全项目仅本文件内部用作去重,无外部读者,已核实)。`last_alarm_sequence` 保留(ALARM 仅 LoRa 出口用,共享无碍)。

修复后 LoRa 与 RPi 各记各的"上次已发序号",两链路独立去重,RPi 正常收到 GNSS/姿态/电池。

## 补充:非 bug 的正常抑制

`GPS_RAW`、`GNSS_DETAIL` 在**首次定位前(`fix_type==0`)本就不发**(避免刷 no-fix 帧),故未锁星时两条链路都不会有 GNSS——属设计行为,非本 bug。室内验证 GNSS 通路需真实定位或能出 fix 的模拟数据。

## 自查:RPi 遥测目录其余编码器无同类隐患

复核 `s_mav_tx_rpi_telem_catalog` 各项:HEARTBEAT/POSITION/BAROALT/SYS_STATUS/GNSSUTC/BAROTEMP/BAROPRES/ENV_HUM 无 sequence 去重(每周期发);MODULE_STATE/MOTOR 分片游标、三个电池 current 去重序号已是 per-target。至此无遗漏共享状态。
