# 修复恢复监视器把 STARTING 当错误、每 2 秒重置 Control 导致滑轨掉档

## 1. 问题

用户现象：电机滑轨拖上去后自己掉回 0；此前记录的"滑两条上去，再滑第三条时四路全部掉下来"属同一原因。

`2026-07-17_05` 遗留的未解释项是"能让四路同时归零的只有 `Px4Lite_ControlClearTargets()`，其调用点已逐个排除"。排查漏掉了一条：`Px4Lite_ControlRecover()`。

## 2. 根因

链路如下：

1. `Px4Lite_SetExternalModuleState()`（`px4lite_modules.c:854`）对**任何非 ONLINE 状态**都累加 `consecutive_errors`，`PX4LITE_STATE_STARTING` 也算。STARTING 是正常启动过程，不是错误。
2. `Px4Lite_ControlRun()` 在 ESC 预解锁分支（`s_esc_armed == 0`）每 20ms（`PX4LITE_CONTROL_PERIOD_MS`）发布一次 STARTING。100ms 就凑满 `PX4LITE_RECOVERY_ERROR_THRESHOLD = 5`。
3. `Px4Lite_RecoveryNeeded()`（`px4lite_recovery.c:31`）判据为 `OFFLINE || FAILED || consecutive_errors >= 5`，第三项与状态无关，于是 STARTING 的 Control 被判定为需要恢复——尽管紧邻的注释写着"STARTING/UNINITIALIZED/DISABLED 交给启动流程处理"。
4. Health 任务的恢复监视器按 `PX4LITE_RECOVERY_DELAY_MS = 2000` 限速，调用 `s_control_descriptor` 注册的 `Px4Lite_ControlRecover()`（`px4lite_app.c:72`）→ `Px4Lite_ControlReset()` → `Px4Lite_ControlClearTargets()`，同时把 `s_arm_start_ms` 拨回当前时刻。

后果有两条，互相锁死：

- **四路目标每 2 秒被清零一次。** Control 发布 `base_percent = 0`，`Display_LoadMotorSnapshot()` 把四条滑轨一起刷回 0%。用户看到的就是"滑上去自己掉下来"，且必然四路同时掉；掉的时刻取决于落在 2 秒窗口的哪个位置，因此早期表现为"有时候"。
- **ESC 永远解锁不了。** `PX4LITE_CONTROL_ESC_ARM_TIME_MS = 2500` > `PX4LITE_RECOVERY_DELAY_MS = 2000`，解锁计时每 2 秒被重新拨回起点，`s_esc_armed` 恒为 0，Control 恒在预解锁分支发布 STARTING，反过来继续喂饱 `consecutive_errors`。硬件输出恒为 1000us 安全脉宽。

该判据只在被调用者放行后才生效，而调用者（`Px4Lite_RecoveryMonitorRun()` 第 53 行）已经在 ONLINE/DEGRADED 时清零并 `continue`。因此 `consecutive_errors >= 5` 这一项**唯一**还能命中的就是 STARTING/UNINITIALIZED/DISABLED——对 OFFLINE/FAILED 它本就是冗余的。它没有任何正确用途，只有这一个副作用。

同一条链路也会打到 `s_estimator_descriptor`（`px4lite_app.c:53`，recover 回调即 `Px4Lite_EstimatorInit`）：Estimator 停在 STARTING 期间同样每 2 秒被重新初始化，姿态零位随之丢失。这与 `2026-07-17_05` 第 4.3 节实测到的"俯仰 +27.0 / 横滚 +10.1，IMU 未做水平校准"现象一致——水平校准会被周期性抹掉。

## 3. 修复

`Framework/Src/px4lite_recovery.c`：`Px4Lite_RecoveryNeeded()` 去掉 `consecutive_errors >= PX4LITE_RECOVERY_ERROR_THRESHOLD` 判据，只按 `OFFLINE || FAILED` 判定，与函数下方既有注释声明的契约一致。函数注释记录了这条陷阱的成因，避免后续再把该判据加回来。

未改动 `Px4Lite_SetExternalModuleState()` 的计数口径：`consecutive_errors` 在全工程只有 `Px4Lite_RecoveryNeeded()` 一个消费者（已用 grep 全量确认），去掉判据后该计数不再参与任何决策，改动它是零收益的额外风险。`PX4LITE_RECOVERY_ERROR_THRESHOLD` 保留在 `px4lite_config.h`，宏未引用不产生告警。

修复后预期时序：Control 在 `Px4Lite_ControlModuleInit()` 后连续预解锁 2500ms → `s_esc_armed = 1` → 发布 ONLINE → 恢复监视器在 ONLINE 分支清零计数并跳过。四路目标只由用户滑轨、下行命令、KEY1 急停、屏上急停和任务饥饿 failsafe 改写，不再被恢复监视器旁路清零。

不改变告警、自检灯、姿态算法、混控与限幅，不改变 OFFLINE/FAILED 模块的恢复行为。

## 4. 验证

**本机没有安装任何 C 编译器（gcc / armcc / Keil 均不存在），本次改动未经过编译或测试执行，为源码级人工审查。** 合入前必须执行：

1. `MDK-ARM/formal_framework.uvprojx` Target 1 Rebuild All，确认 `0 Error(s), 0 Warning(s)`。
2. 实机复测：上电约 2.8s 后电机页四条滑轨应能拖到任意位置并保持不动（此前每 2 秒必掉一次），滑轨下方 `us` 脉宽应随之离开 1000us。
3. 实机确认姿态页水平校准在校准后能长期保持（此前每 2 秒被 `Px4Lite_EstimatorInit` 抹掉）。
4. 姿态零点仍需按 `2026-07-17_05` 第 4.3 节要求，把板子放平后在姿态页手动校准一次；本次修复只保证校准结果不再被周期性重置，不代替校准动作。

## 5. 边界

本次只改恢复判据，不改恢复机制本身：OFFLINE/FAILED 模块仍按 `PX4LITE_RECOVERY_DELAY_MS` 限速无限次重试。若后续需要"模块长时间停在 STARTING 也要救"的能力，应由启动流程自身用独立的启动超时实现，不能再借 `consecutive_errors` 判据，否则会重新引入本文记录的锁死。
