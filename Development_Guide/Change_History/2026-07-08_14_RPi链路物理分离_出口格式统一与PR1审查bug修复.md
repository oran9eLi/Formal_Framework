# 2026-07-08_14_RPi链路物理分离_出口格式统一与PR1审查bug修复

## 背景

承接 `2026-07-07_11/12`（RPi 专属扩展遥测 + 全量出口）与桌面审查记录《Formal_Framework_PR1_RPi对接部分审查》。本轮做三件事：

1. **物理分离**：RPi MAVLink 从与调试口共用的 USART1 迁到独立 USART6（PC6/PC7）。
2. **出口格式统一 + 解耦**：消除 RPi 侧告警/日志双格式冗余；让 RPi 全量出口独立于 LoRa 服务状态。
3. **修 PR#1 审查里 3 个真 bug**（#1 高度传反 / #2 末次 ACK 丢弃 / #4 栈占用）。

全部 RPi 相关代码仍由 `PX4LITE_ENABLE_RPI_MAVLINK` 守卫；无新增源文件，Keil `.uvprojx` 无需改。

---

## 一、RPi 链路物理分离到 USART6

此前 RPi 与调试口共用 USART1，靠 `PX4LITE_DEBUG_USART1_SILENT_FOR_RPI` 软件静音互斥。本次改为独立串口，两者物理分离。

- **BSP**：`bsp_config.h` 新增 `BSP_ENABLE_RPI_UART` 门控 + USART6 引脚段（PC6 TX / PC7 RX，`GPIO_AF8_USART6`，115200 8N1，经 3.3V USB-TTL 连接）；`bsp_uart.c/.h` 新增独立句柄 `huart6` 及 `BSP_RpiUART_Init` / `BSP_RpiUART_Send`（阻塞 TX，无 DMA/IRQ）。**复用现有 `bsp_uart.c`、不新建文件**，以免动 Keil 工程。
- **MSP**：`stm32f4xx_hal_msp.c` 的 `HAL_UART_MspInit/DeInit` 加 USART6 分支（GPIOC + USART6 时钟）。
- **平台层**：`Px4Lite_RpiMavlinkInit/Send` 改调 `BSP_RpiUART_*`，不再碰 USART1。
- **调试口**：`PX4LITE_DEBUG_USART1_SILENT_FOR_RPI` 置 `0U`（共线静音已无必要，保留宏供回退）；USART1 恢复为纯调试口，调试打印正常输出。

引脚核查：PC6/PC7 全板无冲突（I2C/PWM/LCD 的 PIN_6/7 均在别的端口）；USART6 与 USART1 同在 APB2。

## 二、出口格式统一：选择性镜像（消除 RPi 侧双格式冗余）

**问题**：RPi 此前同一份告警/日志会收到两种格式——
- 告警：`ALRMHI/ALRMMSK`（NAMED_VALUE 摘要，来自全量镜像）**和** `RPIALRM`（TUNNEL 0x8001 全量表，专属）。
- 日志：`LOGSYNC`（单条 NAMED_VALUE，镜像）**和** `RPILOG`（TUNNEL 0x8002 批量，专属）。

按决策 D1（全量表），RPi 只认 TUNNEL，那两条镜像的 NAMED_VALUE 被 RPi 侧静默丢弃，纯属占 USART6 带宽的冗余。

**改法**（`px4lite_mavlink_tx.c`）：
- `MavTx_SendPrepared()` 拆出 `MavTx_SendPreparedEx(uint8_t mirror_to_rpi)`；前者是 `mirror=1` 的包装（其余遥测全镜像不变）。
- `MavTx_SendAlarmStatus`（ALRMHI/ALRMMSK）、`MavTx_SendMessageLog`（LOGSYNC）改调 `MavTx_SendPreparedEx(0U)` → **只发 LoRa，不镜像给 RPi**。

结果：RPi 侧告警/日志只剩 TUNNEL 一种格式。**LoRa/屏幕契约完全不动**（这两条仍照发 LoRa），符合方案 A。

## 三、解耦：RPi 全量出口独立于 LoRa（审查 #3）

**问题**：所有 RPi 帧（镜像 + 专属）都在 `Px4Lite_MavlinkTxRun` 内发送，而它 ①只在 `Px4Lite_LoRaService()==OK` 时被调用（`px4lite_modules.c`），②LoRa TX 非空闲即整轮 `return BUSY`。→ LoRa 忙（半双工常态）或 E22 未插时，RPi 全量出口整体停摆，但身份帧（另一条门控）照发，造成"身份有、遥测/告警无"的诡异局部失联，与"RPi 独立全量出口"的设计意图矛盾。

**改法**：
- 把 4 个 RPi 专属项从主 catalog 拆到独立 `s_mav_tx_rpi_catalog[]`，配独立游标 `s_rpi_catalog_index`。
- 新增 `Px4Lite_MavlinkTxRunRpi(now_ms)`：只轮询 RPi 专属 catalog，**不带任何 LoRa 空闲/服务门控**，每次调用最多提交一帧。RPi 专属项经 `MavTx_SendRpiExclusive` 只写 USART6，且会回退 COMM_0 序号，不消耗 LoRa 通道序号。
- `px4lite_modules.c` 的 `Px4Lite_CommWorkRun` 把该函数放到 `LoRaService()==OK` 门控**之外**无条件调用。

结果：LoRa 忙/掉线时，`LORASTAT/RIDSTAT/告警表/日志表` 仍持续送达 RPi。

> **保留的限制**：标准遥测的 RPi 镜像仍随 LoRa 帧走（本质是 LoRa 帧的副本，`SendPrepared` 内产生），故仍受 LoRa 空闲约束——这点未在本轮消除，需彻底解耦须换 MAVLink 原生多通道（见"未处理项 #7"）。本轮保证的是**RPi 专属全量出口**不断流。

## 四、PR#1 审查 bug 修复

### #1 RemoteID 高度字段传反（`px4lite_remoteid_tx.c`）
`OPEN_DRONE_ID_LOCATION` 打包时 `altitude_geodetic`（应为绝对 WGS84 高度）被塞了 home 相对高度差，而 `height`（应为相对起飞点高度，与 `height_reference=OVER_TAKEOFF` 对应）被写死 0 → 飞机爬升后 RemoteID 高度永远 0。
**改**：`altitude_geodetic` 填绝对 `altitude_m`，`height` 填 `(home_valid)?(altitude_m - home):0`，二者对调回正。

### #2 命令末次重试的 ACK 必被丢（`px4lite_mavlink_tx.c` `MavTx_SendPendingCommand`）
原逻辑发出第 5 次（末次）重试后立即 `valid=0`，没等这次的 `COMMAND_ACK` 回来；若末次恰好被接受、ACK 随后到达，`Px4Lite_MavlinkRecordCommandAck` 的 `valid!=0` 检查已失败 → 成功的命令被当失败。
**改**：把"耗尽放弃"分支前置到函数头（`retry_count>=MAX` 且到期才清 `valid`）；每次成功发送都安排下一次唤醒。这样末次尝试同样获得一个完整 `RETRY_MS` 的 ACK 等待窗口，窗口内 ACCEPTED 到达即认领，超时/非 ACCEPTED 再放弃。发送次数仍为 MAX（5）次不变。

### #4 日志表打包栈占用（`px4lite_mavlink_tx.c` `MavTx_PackMessageLogTable`）
调用方 `MavTx_SendRpiMessageLogTable` 的 `mavlink_tunnel_t packet`(133B) 与本函数局部 `Px4Lite_LogEntry_t entries[9]`(~144B) 同时活着，瞬时占栈 ~277B，而 CommTask 栈仅 1536B（`PX4LITE_STACK_COMM=384` words）。
**改**：`entries[]` 改函数内 `static`（本函数仅 CommTask 单线程调用，无重入），移出栈；瞬时占栈峰值降到仅 packet 的 133B。
