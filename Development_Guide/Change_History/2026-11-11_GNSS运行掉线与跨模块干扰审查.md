# GNSS运行掉线与跨模块干扰审查

日期：2026-11-11。V1-GNSS-R02 / V1-E67。本文供固件维护与故障排查人员使用；依据当前E66源码、用户现场描述及主机故障注入记录，不作为现场根因或实板通过证明。

## 现场事实及本轮结论

用户反馈GNSS会自行红色OFFLINE，询问是否有其他代码干扰，希望确认后再修改接线；补充确认红色时Frames原始帧列表停止新增。该观察更需要检查收数/解析是否中断，但UI捕获列表不是独立物理串口字节计数，不能直接据此判定接线坏或DMA停机。

本轮未发现确定的引脚、DMA或外设时钟重复占用；但发现并用故障注入复现两条软件健壮性风险，因此不能给出“代码已完全排除，可以认定接线有问题”的结论。实际现场是否触发尚缺同一时刻计数。

## 跨模块资源核查

| 对象 | 当前资源/结论 |
|---|---|
| GNSS | USART2 PA2/PA3 AF7，DMA1 Stream5 channel4，IRQ优先级6，独占；固定115200/8N1 |
| LoRa / RemoteID | USART3、DMA1 Stream1/3；UART4、DMA1 Stream4，未复用GNSS资源 |
| RGB / 树莓派 | TIM8 PC9、DMA2 Stream7；USART6 PC6/PC7无DMA，未复用GNSS资源 |
| BMI088 | 默认I²C PB6/PB7；备用SPI2 PB13、PC2/PC3，不重配PA2/PA3 |
| 电压电流 / 电机 | ADC PA4/PA5/PC0/PC1；GPIOA直写仅掩码PA6/7，不覆盖GNSS针脚 |
| 新HUD | 显示优先级idle+1，sensor为idle+4；无关闭中断/挂起调度路径，不会因同步写屏本身禁止GNSS IRQ或sensor抢占 |

全局UART回调未将GNSS数据当作其他模块消费。GNSS DMA buffer在`0x2000908C`主SRAM，1024B，未落入CCM。RAW上报hook仅有界复制/队满丢新，Debug在独立低优先级任务读副本，不在sensor或ISR同步打印。正常无定位但有有效报文应黄灯DEGRADED，室内无定位不应直接解释OFFLINE。正常运行不再轮流扫波特率。

## 已复现的软件路径

### 1. 异常长度头令解析器长时间吞掉后续报文

`Sensor/Src/sensor_ubx.c:80`接收完整16位长度后直接进入PAYLOAD；超过本地1016B容量的帧仍消费全部声明载荷及校验，完成后才报告OVERSIZE。当前没有独立半帧期限。`sensor_gnss.c:797`为保证UBX/NMEA隔离，UBX接收期间禁止同时把载荷解释为NMEA，因此长度字段损坏可能让后续真实NMEA被当成UBX载荷。

注入`B5 62 01 35 FF FF`，之后每秒持续输入正确GGA；Driver-only夹具到5000ms已消费252B，但`valid_nmea=1、rx_sequence=1、last_rx_ms=0、framing_busy=1`，没有接受新的完整帧。正常完整流通过测试不覆盖这个坏输入恢复能力。

该复现只跑真实Driver/codec和模拟transport，没有运行Framework/Health的通用软恢复；整机会受到2秒Health重置或6秒链路重探测影响，不能将夹具5000ms直接等同现场持续时间。它说明异常半帧缺少及时恢复的风险，不证明现场收到过这个字节序列，也不将合法超长UBX消息一概视为损坏。修复应设计有界半帧寿命/超长丢弃重同步，同时保持二进制载荷中的伪NMEA隔离。

### 2. TX异常与RX事实发布耦合

`sensor_gnss.c:580`先解析RX，再推进LinkStep；`1198`发现TX busy达2000ms会请求整个RX重建并返回IO_ERROR。版本探测/配置发送失败同样可能触发。`Framework/Src/px4lite_platform_f407.c:578`看到IO_ERROR便提前返回，未读取本轮已更新的接收快照；`px4lite_modules.c:514`只有Adapter成功才更新模块last_rx，超过2000ms则标OFFLINE。

注入完整100B NoFix NAV-PVT且让TX卡住，得到`service=4、rx_sequence=1、last_rx_ms=2000、requested_recovery=1`。这是已收到有效帧仍返回IO_ERROR的确定路径；一次暂态通常下次成功Service可补发，不必然导致持续红灯，持续TX错误/恢复失败才更可疑。UART发送完成与模块协议ACK不同，单独断开TX线通常只会配置未确认，不应将其直接解释成HAL发送错误。

后续修复需要把已收到的有效RX事实与TX/config故障分开处理，同时保留真实硬件故障、配置未确认和恢复计数，不能通过延长离线门限或把红灯改黄掩盖。

## 线路毛刺与恢复时序仍可能参与

`Bsp/Src/bsp_gnss.c:381`的FE/NE/ORE/PE会累计UART错误、停止本GNSS接收并请求sensor重建；硬件接线/供电/噪声可触发这条正常保护路径。第二次错误若落在2秒恢复退避内，等待可能接近OFFLINE门限，出现短红。

1024B在115200/8N1满线下约容纳88.9ms；sensor任务若被同任务其他异常阻塞过久仍可溢出，但当前未找到正常BMI088/气压/电源路径必然造成此类长阻塞的证据。BMI088 I/O超时4ms，初始化等待按状态机推进；ADC异常会提前返回，不是每个失败采样都无限等下去。不能把主机测试通过写成线路故障已经确认。

`PX4LITE_GNSS_RECOVERY_ENABLE=0`只关闭专用旧路径，不等于禁用注册表通用RecoveryMonitor；当前仍按2秒退避请求sensor解析器重置。
