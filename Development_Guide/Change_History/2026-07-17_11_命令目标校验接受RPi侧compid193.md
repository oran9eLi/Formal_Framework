# 2026-07-17_11 命令目标校验接受 RPi 侧 compid 193

## 现象

树莓派经 USART6 下发 `COMMAND_LONG`（命令号 31013，`target_component=193`），命令不执行、且收不到 `COMMAND_ACK`。树莓派侧已排除串口占用、波特率、心跳学习、UART 写入错误，确认超时发生在 ACK 阶段。

## 根因

`Px4Lite_CommandHandleMavlinkLong()` 在进入命令分发前先做目标校验 `Command_IsForThisSystem()`，其 component 判定原本只认 `PX4LITE_MAVLINK_COMPONENT_ID`(191)：

```c
if ((target_component != 0U) && (target_component != PX4LITE_MAVLINK_COMPONENT_ID)) { return 0U; }
```

但本机在 USART6 出口上把自己的 compid 改写为 `PX4LITE_RPI_MAVLINK_COMPONENT_ID`(193)（见 `MavTx_SendRpiExclusive`，心跳、遥测、ACK 全部如此）。树莓派从心跳学到的正是 193，并据此把命令的 `target_component` 填为 193。

于是 193 ≠ 0 且 193 ≠ 191 → 目标校验返回 0 → `Px4Lite_CommandHandleMavlinkLong` 在校验处直接 `return PX4LITE_IDLE`，**既不执行命令，也不排队 ACK**。31013 处理器本身存在且正确，但代码永远走不到分发 switch。

本质是固件端点自相矛盾：在 USART6 上宣告自己是 193，却只接受寻址到 191 的命令。这是 2026-07-17_08 已预警的 191/193 隐患的实锤。

## 修复

新增 `Command_IsForThisComponent()`，把本机在两条链路上对外呈现的两个 compid 都视为"发给本机"：0（广播）、191（LoRa 侧）、193（USART6 侧，仅 `PX4LITE_ENABLE_RPI_MAVLINK` 时）。`Command_IsForThisSystem()` 改用它。

```c
static uint8_t Command_IsForThisComponent(uint8_t target_component)
{
  if (target_component == 0U) { return 1U; }
  if (target_component == (uint8_t)PX4LITE_MAVLINK_COMPONENT_ID) { return 1U; }
#if PX4LITE_ENABLE_RPI_MAVLINK
  if (target_component == (uint8_t)PX4LITE_RPI_MAVLINK_COMPONENT_ID) { return 1U; }
#endif
  return 0U;
}
```

同一校验也用于接收方向的 `Px4Lite_CommandHandleMavlinkAck()`（本机作为发起方收 ACK 时）。放宽后"发给本机 193 的 ACK"也被接受，方向一致，无副作用。

`target_system` 判定不变（0 或本机 UID 派生 sysid）。

## 影响面

| 文件 | 改动 |
|---|---|
| `Framework/Src/px4lite_command.c` | 新增 `Command_IsForThisComponent`，目标校验接受 191/193/0 |
| `Development_Guide/树莓派下行MAVLink电机控制帧格式.md` | `target_component` 说明更新为 0/193/191 均接受，推荐沿用心跳学到的 193 |

宏可见性已核对：`px4lite_command.c` 已 include `px4lite_config.h`，`PX4LITE_ENABLE_RPI_MAVLINK`、`PX4LITE_MAVLINK_COMPONENT_ID`、`PX4LITE_RPI_MAVLINK_COMPONENT_ID` 均无条件定义于该头。

## 树莓派侧

无需改动即可打通：工具当前用 `target_component=193` 现在会被接受，31013 会执行并回 ACK。ACK 的 `target_system=250`/`target_component=191` 原样回填工具的来源，符合工具的接受条件。若愿意，`target_component` 也可改用 0 或 191，行为一致。

## 与 31013 参数的关系

命令能过目标校验后，`Command_HandleSetMotorPulseUs`(31013) 会要求 param1..4 落在 ESC 脉宽区间 [`PX4LITE_CONTROL_ESC_MIN_PULSE_US`, `PX4LITE_CONTROL_ESC_MAX_PULSE_US`]，否则回 `MAV_RESULT_DENIED`（仍有 ACK）。故修复后若仍见 DENIED，应检查脉宽取值，而非链路。

**未执行 Keil build。** 本机无任何可用 C 编译器（`UV4.exe`/`armcc`/`armclang`/`gcc`/`arm-none-eabi-gcc` 均不存在），仓库无 CLI/CMake/Makefile 入口。已静态核对：新函数逻辑自洽、宏在该编译单元可见、`PX4LITE_ENABLE_RPI_MAVLINK=0` 时退化为原 191/0 行为。合入前需在装有 Keil 的机器上 Rebuild All 并确认 `0 Error(s), 0 Warning(s)`，随后用树莓派实发 31013 验证命令执行并收到 ACK。
