# 2026-07-08_17_修复RPi帧CRC重算漏最后一字节(致命)

## 现象

真实开发板接树莓派后,`cns_rpi` 无任何解码输出;同一根线接电脑串口助手能看到数据。排查报告(《树莓派串口收不到数据-排查报告》2026-07-08)证据链:

1. 树莓派 `cat /dev/ttyUSB0` 裸抓能看到完整正常的 MAVLink v2 帧(0xFD 起始,MODSTAT1/LORASTAT/RIDSTAT/DCDW-001 等字符串清晰)——物理层/波特率/CH340 都正常。
2. `strace` 证明 `cns_rpi` 确实 `read()` 到了这些字节。
3. 用独立实现 `pymavlink` 接同一路数据:**连续 70+ 帧 100% BAD_DATA,全是 CRC 校验失败**,覆盖 HEARTBEAT/SYS_STATUS/ATTITUDE/BATTERY_STATUS/NAMED_VALUE_INT/TUNNEL 各类。
4. pymavlink 按官方 common 方言现算的 CRC 与帧尾实收 CRC 对不上 → **发送端(STM32 固件)附在帧尾的 CRC 本身就是错的**,且对所有消息类型都错。

## 根因

RPi 链路的帧要改写 compid=193 + RPi 独立序号,之后必须重算 CRC——由手写函数 `MavTx_RecomputeChecksum`(`px4lite_mavlink_tx.c`)完成。**只有 RPi 出向帧走这条手算路径;LoRa 帧用库函数 `mavlink_msg_to_send_buffer` 保留库算的正确 CRC,故 LoRa 不受影响、仅 RPi 链路全错。**

Bug 在 CRC 累加范围:

```c
/* 错误 */
checksum = crc_calculate(&header[1], (uint16_t)(header_len - 1U));
```

MAVLink CRC 覆盖"核心头(不含 STX) + payload + CRC_EXTRA"。核心头长度:
- v2 = `MAVLINK_CORE_HEADER_LEN` = **9**(len, incompat, compat, seq, sysid, compid, msgid×3)
- v1 = `MAVLINK_CORE_HEADER_MAVLINK1_LEN` = **5**(len, seq, sysid, compid, msgid)

代码把这些核心字节放在 `header[1..header_len]`(`header[0]` 是 STX,不进 CRC)。因此应对 `header[1..header_len]` 共 `header_len` 个字节算 CRC,但 `header_len - 1U` **少算 1 字节,漏掉最后一个核心头字节**:v2 漏 `msgid` 高字节(`header[9]`)、v1 漏 `msgid`(`header[5]`)。

即便该字节为 0(如 HEARTBEAT msgid=0),CRC16 少喂 1 个字节,结果也不同 → **每一帧 CRC 都错**,与报告"所有消息类型全 BAD_DATA"完全吻合。

## 修复

```c
/* 正确:覆盖全部 header_len 个核心头字节 header[1..header_len] */
checksum = crc_calculate(&header[1], (uint16_t)header_len);
```

一字符级改动(去掉 `- 1U`)。修复后手算序列与官方一致:`crc_calculate(核心头 header_len 字节)` → `crc_accumulate_buffer(payload, len)` → `crc_accumulate(CRC_EXTRA)`。

## 影响

- 这是 **RPi 链路自始未跑通的根因**:树莓派一直能收到字节,但所有帧因 CRC 不过被(正确地)丢弃,故"收不到数据"。`cns_rpi` 侧无 bug。
- 修复面覆盖**全部 RPi 出向帧**:RPi 遥测/专属帧(`MavTx_SendRpiExclusive`)与 RemoteID 身份镜像(`Px4Lite_MavlinkTxMirrorToRpi`)都用同一手算函数,一并修好。
- LoRa / RemoteID(UART4)链路不受影响(它们不走手算 CRC)。

## 改动文件

- `Framework/Src/px4lite_mavlink_tx.c`:`MavTx_RecomputeChecksum` 的 `crc_calculate` 长度 `header_len - 1U` → `header_len`,并加注释。

## 构建与验证

- 需重新编译。
- **验证**:① 树莓派 `pymavlink tools/mavlink_sim/receive_frames.py` 接实机,确认由 100% BAD_DATA 变为正常解码(CRC 通过);② `cns_rpi` 出现遥测/扩展帧解码输出;③ 抽验 HEARTBEAT 一帧,实收 CRC == pymavlink 现算 CRC。

## 关联

- 审查记录曾把这套"手写 CRC + 改 compid/seq"标为架构隐患(#7,建议改用 MAVLink 原生 `COMM_1` 多通道)。本 bug 正是该手算路径的实证。原生多通道重构可彻底移除手算 CRC,作为后续项(非本次)。
