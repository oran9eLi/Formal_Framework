# Formal Framework 架构设计与后续开发汇报

## 1. 汇报结论

本次架构调整的目标不是简单增加模块，而是建立一套可以持续接入 GNSS、
IMU、气压计、电源、Display、LoRa、5G、SD 卡和未来 Linux A 核的统一
开发框架。

当前已经完成：

- 建立可独立编译的 STM32F407 + FreeRTOS 工程。
- 跑通 ATGM336H 的 USART2 DMA、IDLE、中断、NMEA 解析和发布链路。
- 支持 GPS 与北斗可见星、参与定位星、位置、速度和定位状态。
- 建立 BSP、Sensor、Framework、Business 分层。
- 建立 Measurement、Domain、Status、Topic 和应用只读快照接口。
- 建立固定任务集合、健康检查基础、调试接口和异常 hooks。
- ARMCC 5.06 全量构建结果为 `0 Error / 0 Warning`。

当前并非完整产品：

- GNSS 是目前唯一真实闭环的传感器。
- Estimator 目前只完成基础导航转换，不是正式融合算法。
- Display、Alarm、Logger、Command 等仍有占位或骨架内容。
- LoRa、5G、SD 卡、IMU、气压计和 Linux IPC 尚待真实接入。

## 2. 为什么调整架构

原有开发方式可以快速验证单个驱动，但随着模块增加，会出现以下问题：

1. 驱动、任务、业务和调试代码互相调用，责任边界不清晰。
2. 一个传感器增加一个任务，任务栈和 FreeRTOS heap 持续扩大。
3. 上层直接读取驱动变量或 DMA 缓冲区，可能读到半包或撕裂数据。
4. 调试流程能工作，正式任务流程却没有持续调用解析和更新函数。
5. 多个任务重复读取同一设备，导致数据所有权不明确。
6. 状态机分散在驱动、Framework 和应用层，离线状态可能不一致。
7. 通信和日志直接复制大结构体，增加栈、时延和版本兼容风险。
8. 新模块只考虑正常数据，没有统一考虑超时、恢复、告警和降级。

因此，本次调整重点是固定边界、所有权和数据交换方式，而不是堆叠更多
任务和接口。

本图使用纯文本绘制，普通 Markdown 查看器也可以直接显示。可编辑的
Mermaid 源码保存在 `08_架构设计与后续开发汇报_总体架构图.mmd`。

核心调用方向：

```text
Task -> Framework API -> Platform Adapter -> Driver -> BSP -> HAL
```

数据返回方向：

```text
完整原始输入
-> 校验和解析
-> Measurement
-> Topic/FIFO
-> 运算后的 Domain Snapshot
-> Application API
-> Display/LoRa/5G/Logger
```

任何上层任务不得直接读取 DMA 缓冲区、驱动私有变量或另一个任务的局部
数据。

## 4. 各层职责

| 层级 | 负责内容 | 不负责内容 |
|---|---|---|
| BSP | 引脚、时钟、UART/I2C/SPI、DMA、中断、字节收发 | NMEA 解析、业务状态、显示和告警策略 |
| Sensor/Driver | 芯片协议、校验、标定、设备数据和错误事实 | 创建业务任务、LoRa 发送、页面刷新 |
| Platform Adapter | 把不同驱动转换成 Framework 固定格式 | 重复实现驱动协议 |
| Framework | 采集调度、Topic、FIFO、状态汇总、健康监控 | 具体页面和业务协议 |
| Domain/Estimator | 时间对齐、过滤、运算和融合 | 访问 DMA 和硬件寄存器 |
| Business | 提供应用快照、事件分发和业务编排 | 直接调用 BSP 或驱动私有函数 |
| Service | Display、通信、日志和报警输出 | 修改传感器内部状态 |

## 5. 如何规避之前的问题

### 5.1 `BASEPRI` 屏蔽中断导致 GNSS 不再接收

问题表现：

- DMA `NDTR` 变化，但 USART2 和 DMA 中断一直 pending。
- GNSS 中断计数不增加，正式流程持续打印 no data。
- `BASEPRI=0x80` 屏蔽了配置优先级较低的外设中断。

规避方式：

- 临界区必须短，只保护索引或小结构复制。
- 进入临界区前保存原中断状态，退出时恢复原状态。
- 禁止在通用函数中无条件调用 `__enable_irq()`。
- ISR 中禁止解析、打印、等待和慢速外设访问。
- Health 后续监测中断计数、DMA 位置和数据序号是否持续推进。

### 5.2 调试能解析，正式流程却一直 no data

问题原因：

- 调试函数内部主动调用了接收、解析或更新函数。
- 正式任务只调用读取接口，没有持续推进驱动状态机。
- 单次启动打印不能证明周期任务仍在运行。

规避方式：

- 每个驱动固定为 `Init / Service / CopySnapshot / GetStatus`。
- 只有采集任务周期调用 `Service()`。
- 调试代码只读取快照和计数，不承担正式数据推进职责。
- 关闭调试宏后，采集、解析、发布和状态更新逻辑保持不变。
- 通过 `sequence`、任务心跳和最后更新时间证明链路持续运行。

### 5.3 数据读取一半或结构体撕裂

问题原因：

- 写任务正在更新结构体，读任务同时复制。
- 上层直接访问驱动全局变量。
- 时间戳、位置和状态可能来自不同次更新。

规避方式：

- 低频小数据使用 Latest Snapshot 和短临界区完整复制。
- 较大数据使用双缓冲、发布索引或奇偶版本号。
- 高频连续数据使用固定 FIFO，不用单一最新值代替数据流。
- 写者完成全部字段后才递增 `sequence` 并发布。
- 应用通过 `App_CopyNavigation()` 等 API 获取一致快照。

### 5.4 任务栈过大和任务数量持续增加

问题原因：

- 一个设备创建一个永久任务。
- 任务局部定义大数组、通信帧和日志块。
- 使用大栈掩盖格式化输出、深调用和不合理局部变量。

规避方式：

- 同类传感器由统一采集任务按周期表调度。
- 高频采集、普通采集、融合、健康、通信和日志按实时性归并。
- 大帧和日志块使用静态专属 buffer 或固定内存池。
- 新增任务必须提交周期、优先级、最坏执行时间和栈预算。
- 使用 `uxTaskGetStackHighWaterMark()` 验证，不盲目扩大栈。

### 5.5 周期漂移和长时间运行后输出停止

问题原因：

- 周期任务使用 `vTaskDelay()`，执行时间不断叠加。
- 慢速打印、屏幕刷新或通信发送阻塞任务。
- 单次循环处理数据无上限，其他任务被长期占用。

规避方式：

- 周期任务统一使用 `vTaskDelayUntil()`。
- 每次循环限制最大处理条数和最大运行预算。
- Display、通信和 Logger 使用非阻塞状态机或独立服务任务。
- 调试打印限频，长期稳定性测试禁止持续打印原始 NMEA。
- Health 记录 deadline miss、最长执行时间和任务心跳。

### 5.6 GNSS 状态判断重复

问题原因：

- 驱动和 Framework 同时判断在线、离线和超时。
- 两套状态机使用不同时间和规则，可能产生冲突。

规避方式：

- Driver 只提供“是否收到、是否校验通过、是否定位”等设备事实。
- Framework Health 统一判断超时、离线、降级和恢复。
- Business 只读取统一状态，不重新实现超时判断。
- 所有状态变化带版本、发生时间、故障码和恢复计数。

### 5.7 告警被后续低级事件关闭

问题原因：

- 按队列最后一条事件直接开关蜂鸣器。
- `CRITICAL` 后到达一条 `INFO`，可能错误关闭告警。

规避方式：

- Event Queue 只传递状态变化事件。
- Alarm Manager 维护活动告警表。
- 输出动作取全部活动告警中的最高严重度。
- 告警支持去重、升级、锁存、确认、恢复和清除。

### 5.8 通信发送半帧或数据版本不一致

问题原因：

- 把 C 结构体内存直接作为协议发送。
- UART、LoRa 或 5G 部分发送被误认为整帧成功。
- 发送过程中源快照被下一次发布覆盖。

规避方式：

- 使用固定协议帧头、版本、长度、序号、时间戳和 CRC。
- 编码前复制一份完整应用快照。
- 发送状态机维护 `offset`，直到完整长度发送完毕才成功。
- 大帧使用内存池，发送完成前不得归还或覆盖。
- 接收端只在长度、版本和 CRC 全部通过后发布完整消息。

### 5.9 时间单位和“新数据”判断错误

问题原因：

- Tick 被命名为 `_ms`，调用者误以为是真实毫秒。
- 仅依赖时间戳判断新数据，回绕或同一时刻可能漏数据。
- `GetUs()` 名称暗示微秒精度，实际只有毫秒分辨率。

规避方式：

- `_ms`、`_us`、`_ticks` 必须与真实单位一致。
- 数据更新优先使用单调递增 `sequence`。
- Tick 只用于 RTOS 内部调度，公共数据使用平台时间接口。
- 时间回绕比较统一使用无符号差值。

## 6. 后续开发统一方法

每个新模块按以下顺序接入：

1. 定义型号、引脚、总线、DMA、中断和资源所有权。
2. 定义原始数据、工程值、单位、范围、频率和最大年龄。
3. 选择 Snapshot、FIFO、Event Queue 或 Memory Pool。
4. 完成 BSP，只验证硬件传输。
5. 完成 Driver，只验证协议、校验、标定和设备事实。
6. 通过 Platform Adapter 转换成 Framework 固定数据格式。
7. 加入现有采集任务周期表，优先不新增任务。
8. 加入状态、超时、恢复、错误计数和故障码。
9. 加入 Domain 运算和应用只读 API。
10. 最后接入 Display、通信、日志和告警消费者。
11. 完成断线、半包、CRC 错、队列满、DMA 卡死和恢复测试。
12. 完成编译、栈水位、heap、长稳和版本归档。

## 7. 临时新增任务的准入规则

临时验证任务也不能随意加入正式任务集合。新增前必须确认现有任务是否
可以通过周期调度项完成。

只有满足以下任一条件才允许新增任务：

- 外设 API 存在不可避免的独立阻塞。
- 模块具有明显不同的实时优先级或 deadline。
- 必须独占不可重入硬件或协议资源。
- 最坏执行时间会破坏已有任务周期。
- 功能需要独立故障隔离和心跳监控。

新增任务必须同时登记：

| 项目 | 必填内容 |
|---|---|
| 名称 | 唯一任务名称 |
| 所有者 | 负责模块和开发人员 |
| 周期 | 固定周期或事件触发条件 |
| 优先级 | 与现有任务的关系 |
| 栈预算 | 初始值和测量依据 |
| 最坏执行时间 | 正常和异常路径 |
| 阻塞点 | 队列、信号量、外设等待 |
| 数据输入 | Topic、FIFO、Event 或 Pool |
| 数据输出 | 发布对象和消费者 |
| 心跳 | Health 检测位置 |
| 删除条件 | 临时验证结束后是否移除 |

临时任务禁止：

- 直接访问另一个任务的局部或私有数据。
- 在循环中无延时空转。
- 长时间关闭中断或调度器。
- 持锁执行打印、HAL 阻塞发送、屏幕刷新或 SD 写入。
- 使用大局部数组规避内存所有权设计。
- 把测试函数变成正式数据链路的必要组成部分。

## 8. 架构优势

1. **扩展清晰**：新设备按相同层级和模板接入，不需要重新设计调用关系。
2. **数据完整**：Snapshot、FIFO、Queue 和 Pool 分别覆盖不同数据特性。
3. **任务可控**：优先复用固定任务，避免任务数量和栈持续膨胀。
4. **故障可定位**：状态、时间、序号、错误计数和心跳能够定位链路断点。
5. **业务解耦**：Display、LoRa、5G、日志读取同一应用快照。
6. **调试独立**：关闭调试后不改变正式采集、解析和发布流程。
7. **适合演进**：未来 Linux A 核通过稳定消息边界接入，不侵入底层驱动。
8. **便于协作**：不同人员可以在明确目录、接口和所有权下并行开发。

## 9. 当前局限和风险

这套架构不是“代码放进去就自动可靠”，仍依赖以下内容真正落地：

- Alarm Manager、POST、Watchdog 和异常记录尚未完成。
- IMU、气压计、电源接入后，现有任务周期和优先级需要重新测量。
- 高频数据必须实测 FIFO 深度和最坏消费延迟。
- Snapshot 变大后不能继续使用长临界区整结构复制。
- Display、SD 和蜂窝通信必须实现非阻塞或分步状态机。
- 融合算法必须处理时间对齐、质量、异常值和数据源降级。
- 后续每次新增模块都必须重新检查 RAM、Flash、heap、栈和 CPU 预算。

因此，架构的价值是让风险有统一处理位置，不代表风险已经全部消失。

## 10. 团队强制注意事项

1. 驱动归驱动，任务归 Framework，业务归 Business。
2. 不允许跨层直接读取 DMA、寄存器或驱动私有变量。
3. 不允许一个传感器默认创建一个任务。
4. 不允许用扩大栈和 heap 代替原因分析。
5. 不允许发布尚未完整校验或尚未计算完成的数据。
6. 不允许关闭调试宏后正式流程停止工作。
7. 不允许直接发送 C 结构体内存。
8. 不允许忽略返回值、超时、队列满和部分发送。
9. 不允许使用含义不明确的时间单位和状态。
10. 不允许仅凭编译通过就宣布模块完成。
11. 所有新增任务、静态 buffer、DMA 和队列都必须有唯一所有者。
12. 所有模块必须同时提交正常流程、异常流程和恢复流程。

## 11. 下一阶段计划

优先级建议：

1. 完成自研 API 函数级文档和模块接口定版。
2. 完成 POST、模块注册、Alarm Manager 和 Health Monitor。
3. 按统一模板接入 IMU，并验证 FIFO、时间戳和任务预算。
4. 接入气压计和电源，形成完整健康快照。
5. 完成 Display 的真实适配。
6. 完成统一通信协议后接入 LoRa 和 5G。
7. 完成 Logger、SD 卡和黑匣子记录。
8. 启用心跳门控看门狗并执行 24/72 小时稳定性测试。
9. 最后定义与 Linux A 核的 IPC，保持 MCU 可独立运行。

## 12. 汇报结束语

当前架构已经从“单驱动验证工程”升级为“以数据完整性、固定任务集合、
统一状态和应用快照为核心的可扩展框架”。下一步的重点不是继续增加
目录和接口，而是按照统一模板逐个完成真实模块、异常闭环和长期验证。
