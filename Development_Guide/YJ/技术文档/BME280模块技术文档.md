## 1. 模块定位

BME280 用于采集环境温度、气压、相对湿度，是 CNS 平台"电源/环境感知"能力的低频传感器载体，同时是
"高度"这个导航量的间接来源——气压值经标准大气模型换算成气压高度，供 Estimator 判断垂直方向变化。

模块本身**不做任何解算**：寄存器里存的是未补偿的 20/16 位原始 ADC 值，真正的温度/气压/湿度换算需要
代入芯片出厂烧录、每颗芯片各不相同的补偿参数，这一步在本工程的 Sensor Driver 层完成，不在模块内部。
模块接入统一的 `sensor` 采集任务，不单独创建 FreeRTOS 任务。

正式数据链路：

```text
BME280 (I2C1)
  -> BSP_I2C           (寄存器读写、总线恢复)
  -> Sensor_BME280     (芯片 ID 校验、补偿参数读取、强制测量触发、补偿计算)
  -> px4lite_platform_f407.c   (驱动快照 -> 框架 Baro 测量, sequence 去重, 气压→高度、高度差分→垂直速度)
  -> Baro Topic                (Latest Snapshot 发布)
  -> Health / Storage / Business / Display
```

> 注意：气压→高度、高度差分→垂直速度这两步计算不在 Sensor Driver 里，而是在 Platform Adapter
> （`px4lite_platform_f407.c`）完成，见 §5.3——这是 BME280 和典型样板 A 模块（比如只做"寄存器换算成
> 工程单位就完事"的传感器）不太一样的地方，值得单独说明避免以后有人以为这段逻辑漏了或者应该搬到
> Sensor 层。

## 2. 硬件与总线

| 项目 | 配置 |
|---|---|
| 器件 | BME280（Bosch Sensortec，温度/气压/湿度三合一） |
| 总线 | I2C1，PB6/SCL、PB7/SDA，100 kHz |
| I2C 地址 | 自动探测 `0x76`（主，`SDO` 接地）或 `0x77`（备，`SDO` 接 VDD） |
| 采集周期 | 1000 ms（`sensor` 任务节拍下的工作周期，见 `PX4LITE_BARO_WORK_PERIOD_MS`；气压/温湿度变化本就慢，不需要按 IMU 的 10 ms 采） |
| 所属任务 | `sensor` |

**总线约束**：BME280 与 MPU6050 共用 I2C1，BSP 层只负责 I2C 读写和总线恢复，不解析芯片寄存器语义；
寄存器地址、补偿参数解读全部在 Sensor 层。多设备共总线的上拉/时序注意事项见 §11 踩坑案例 1。

## 4. 协议 / 数据格式

BME280 是标准 I2C 从设备，没有帧头/校验和这类协议包装，交互就是"写寄存器地址 → 读连续字节"。

**关键寄存器地址**（摘自 `Sensor/Src/sensor_bme280.c:15-27`）：

```c
#define BME280_I2C_ADDR_PRIMARY     (0x76U << 1)
#define BME280_I2C_ADDR_SECONDARY   (0x77U << 1)

#define BME280_REG_CALIB_TP   0x88U  /* 温度/气压补偿参数，连续 26 字节 */
#define BME280_REG_CALIB_H1   0xA1U  /* 湿度补偿参数第 1 项，1 字节 */
#define BME280_REG_ID         0xD0U  /* 芯片 ID，期望值 0x60 */
#define BME280_REG_RESET      0xE0U  /* 写 0xB6 触发软复位 */
#define BME280_REG_CALIB_H2   0xE1U  /* 湿度补偿参数第 2~6 项，连续 7 字节 */
#define BME280_REG_CTRL_HUM   0xF2U  /* 湿度过采样配置，写这个寄存器后必须再写 CTRL_MEAS 才生效 */
#define BME280_REG_STATUS     0xF3U  /* bit0=校准参数更新中(im_update)，bit3=测量中(measuring) */
#define BME280_REG_CTRL_MEAS  0xF4U  /* 温度/气压过采样 + 工作模式（强制/正常/休眠），写这个寄存器触发测量 */
#define BME280_REG_CONFIG     0xF5U  /* standby 时间、IIR 滤波系数 */
#define BME280_REG_DATA       0xF7U  /* 测量结果起始地址，连续 8 字节（气压3+温度3+湿度2） */

#define BME280_I2C_TIMEOUT_MS   20U   /* 常规寄存器读写单次超时 */
#define BME280_PROBE_TIMEOUT_MS 4U    /* 地址探测（IsDeviceReady）超时，比常规读写短，见下方说明 */
```

> **历史"20 → 4"疑点已查明**：`Development_Guide/Change_History/2026-06-12_21_I2C阻塞与显示卡死修复.md`
> 记录过"`BME280_I2C_TIMEOUT_MS` 20 → 4"。核对当前源码（`sensor_bme280.c:40-41`）确认：这里其实是
> **两个不同的超时宏**——常规寄存器读写用 `BME280_I2C_TIMEOUT_MS`（仍为 `20U`），地址探测
> （`BSP_I2C_IsDeviceReady`）用另一个宏 `BME280_PROBE_TIMEOUT_MS`（`4U`）。历史那个"4"落在了探测路径上
> （探测失败要快速跳到备用地址，短超时更合理），常规传输超时保持 20 未变。两者并存、不矛盾。

**强制测量配置**（BME280 没有"自动连续采样"，每次要读新数据必须先写 `CTRL_MEAS` 触发一次强制测量）：

```c
#define BME280_OSRS_X1              0x01U
#define BME280_MODE_FORCED          0x01U
#define BME280_CTRL_MEAS_FORCED_X1  ((BME280_OSRS_X1 << 5) | (BME280_OSRS_X1 << 2) | BME280_MODE_FORCED)
#define BME280_CTRL_HUM_X1          BME280_OSRS_X1

static Bme280_Result_t Bme280_ConfigureForcedMode(void)
{
  if ((Bme280_WriteReg(BME280_REG_CTRL_HUM, BME280_CTRL_HUM_X1) != BSP_STATUS_OK) ||
      (Bme280_WriteReg(BME280_REG_CONFIG, BME280_CONFIG_STANDBY_0_5MS) != BSP_STATUS_OK) ||
      (Bme280_WriteReg(BME280_REG_CTRL_MEAS, BME280_CTRL_MEAS_FORCED_X1) != BSP_STATUS_OK)) {
    return BME280_RESULT_IO_ERROR;
  }
  return BME280_RESULT_OK;
}
```

> 上面这段是源码原样摘录，源码本身没有注释。唯一有强制顺序要求的是 **`CTRL_MEAS` 必须最后写**——
> 只有写它才会锁存 `CTRL_HUM` 的配置并触发本次测量；`CTRL_HUM` 和 `CONFIG` 两者谁先谁后不影响正确性，
> 这里只是代码恰好这么排列，不代表这个顺序是必须的，写文档时不要把"代码长这样"和"必须这样写"混为
> 一谈。

**8 字节测量数据块的位打包格式**（气压/温度各 20 位、湿度 16 位，大端、右对齐）：

```c
uint8_t data[8];
Bme280_ReadReg(BME280_REG_DATA, data, sizeof(data));
int32_t adc_P = (int32_t)((((uint32_t)data[0]) << 12) | (((uint32_t)data[1]) << 4) | (((uint32_t)data[2]) >> 4));
int32_t adc_T = (int32_t)((((uint32_t)data[3]) << 12) | (((uint32_t)data[4]) << 4) | (((uint32_t)data[5]) >> 4));
int32_t adc_H = (int32_t)((((uint32_t)data[6]) << 8) | data[7]);
```

**补偿计算**：ADC 原始值必须用芯片出厂烧录、每颗芯片各不相同的补偿参数（`dig_T1~T3`/`dig_P1~P9`/
`dig_H1~H6`，从 `CALIB_TP`/`CALIB_H1`/`CALIB_H2` 三段寄存器读出）代入 Bosch 官方补偿公式才能得到真实
工程量。公式本身是较长的定点数运算（刻意用整数移位避免浮点开销），完整实现见
`Bme280_CompensateTemperature`/`Bme280_CompensatePressurePa`/`Bme280_CompensateHumidity` 三个函数
（`sensor_bme280.c:181-235`）。这段定点运算的位移量、运算结构和 Bosch 官方 datasheet 附录里公开的
参考补偿算法高度相似（变量命名 `dig_T1~T3`/`dig_P1~P9`/`dig_H1~H6`、`s_t_fine` 中间量都是 Bosch 参考
实现的标准写法），**但本次核对没有拿到实际 datasheet 原文逐行比对**，这是推断不是确认过的事实，写
正式文档或后续维护如果要改动这几个函数，建议先找 datasheet 原文核对，不要凭这段代码"看起来像"就
认定它完全正确。可以确认的事实是：改动前后必须保证数值结果不变（比如拿已知参考气压/温度值验证），
抄错位移量或运算顺序不会报错，只会让读数悄悄跑偏。三个函数共用一个中间量 `s_t_fine`（温度补偿计算
副产物），气压/湿度补偿必须在温度补偿之后调用，顺序不能颠倒——这一点是读代码直接看出的调用依赖关系，
是确认过的事实。

## 5. 采样 / 处理流程

### 5.1 初始化（`Sensor_BME280_Init()`）

1. 探测 I2C 地址：先试 `0x76`，`BSP_I2C_IsDeviceReady` 超时则试 `0x77`（`Bme280_ProbeAddress`）。
2. 读 `REG_ID`，校验芯片 ID 是否为 `0x60`（`Bme280_CheckChipId`），不是则返回 `BME280_RESULT_BAD_ID`。
3. 写 `REG_RESET=0xB6` 触发软复位，延时 2 ms。
4. 轮询 `STATUS` 寄存器 bit0（`im_update`）清零，最多轮询 20 次、每次间隔 1 ms，超时返回
   `BME280_RESULT_TIMEOUT`（`Bme280_WaitStatusClear`）。
5. 读取全部补偿参数（26+1+7 字节，`Bme280_ReadCalibration`），校验 `dig_P1 != 0`（读到全零通常意味着
   总线读错了地址或时序）。
6. 调用 `Bme280_ConfigureForcedMode()` 配置强制测量模式，成功后置 `s_initialized=1`。

### 5.2 运行阶段（`Sensor_BME280_Service(now_ms)`，一次完整测量跨多次调用完成）

这是本模块和很多"一次 Service 调用就能拿到新数据"的模块不同的地方——BME280 一次强制测量典型耗时
几毫秒到十几毫秒，**不能**在 `Service()` 里原地阻塞等待（会拖住 `sensor` 任务的其他传感器采集），所以
实现是一个横跨多次调用的两阶段状态机：

```c
typedef enum { BME280_MEASURE_IDLE = 0, BME280_MEASURE_WAITING } Bme280_MeasureState_t;
```

- **第一次调用**（`s_measure_state == IDLE`）：调用 `Bme280_ConfigureForcedMode()` 触发一次新测量，
  记录 `s_measure_start_ms = now_ms`，状态切到 `WAITING`，本次直接返回 `BME280_RESULT_NO_DATA`（不
  阻塞）。
- **后续调用**（`s_measure_state == WAITING`）：先检查 `now_ms - s_measure_start_ms` 是否达到
  `BME280_MEASURE_DELAY_MS`（10 ms，给测量留出最短耗时），没到继续返回"无数据"；到了才去读 `STATUS`
  寄存器 bit3（`measuring`），仍在测量中且未超过 `BME280_MEASURE_TIMEOUT_MS`（30 ms）继续等；超时则
  记一次失败并把状态打回 `IDLE`（下次调用重新触发测量，不是死等）。
- 测量完成（`measuring` 位清零）：一次性读 8 字节数据块，代入补偿公式换算，写入 `s_snapshot`，
  `rx_sequence++`，状态打回 `IDLE`，等待下一轮触发。

写快照那一段用了"临界区外准备好完整候选值、临界区内只做整体赋值"的写法（`sensor_bme280.c:388-406`），
不在临界区里做浮点运算：

```c
Bme280_Snapshot_t candidate;
uint32_t primask;

primask = BSP_Critical_Enter();
candidate = s_snapshot;
BSP_Critical_Exit(primask);

candidate.rx_sequence++;
if (candidate.rx_sequence == 0U) { candidate.rx_sequence = 1U; }  /* 防止 32 位序号绕回 0——0 在这个
                                                                       工程里是 CopySnapshot()/GetStatus()
                                                                       判定"尚无数据"的哨兵值，见 §6 */
candidate.sample_time_ms        = now_ms;
candidate.temperature_c         = Bme280_CompensateTemperature(adc_T);
candidate.pressure_pa           = Bme280_CompensatePressurePa(adc_P);
candidate.relative_humidity_pct = Bme280_CompensateHumidity(adc_H);

primask = BSP_Critical_Enter();
s_snapshot = candidate;
BSP_Critical_Exit(primask);
```

### 5.3 Platform Adapter：气压 → 高度 → 垂直速度（`px4lite_platform_f407.c`）

Sensor 层只产出温度/气压/湿度三个直接补偿量，**气压高度**和**垂直速度**是 Platform Adapter 在
`Px4Lite_BaroRead()` 里额外算出来的，Sensor 层不做这一步。

**标准大气模型换算气压高度**（气压值在合理范围内才换算，避免用坏数据算出离谱高度）：

```c
static int32_t Px4Lite_BaroPressureToAltitudeMm(float pressure_pa)
{
  float ratio;
  float altitude_m;

  if (pressure_pa <= 0.0f) { return 0; }  /* 防除零/防负数，气压异常时直接返回 0 而不是算出 NaN 或负高度 */

  ratio      = pressure_pa / PX4LITE_BARO_SEA_LEVEL_PA;   /* 101325.0f Pa，标准海平面气压 */
  altitude_m = 44330.0f * (1.0f - powf(ratio, 0.19029495f));
  return Px4Lite_RoundFloatToI32(altitude_m * 1000.0f);
}
```

**高度差分算垂直速度**，带跳变限幅和一阶低通平滑，抑制气压噪声引起的速度抖动：

```c
static int32_t Px4Lite_BaroUpdateVerticalSpeed(int32_t altitude_mm, uint32_t sample_time_ms)
{
  /* 首帧或时间戳异常：只记录基准，不产出速度 */
  ...
  dt_ms = sample_time_ms - s_baro_last_sample_ms;
  if (dt_ms <= PX4LITE_BARO_MAX_AGE_MS) {
    int32_t delta_mm = altitude_mm - s_baro_last_altitude_mm;
    /* 单次高度跳变限幅在 ±PX4LITE_BARO_MAX_JUMP_MM（20000mm）内，防止脏数据算出异常速度 */
    delta_mm = Px4Lite_ClampI32(delta_mm, -PX4LITE_BARO_MAX_JUMP_MM, PX4LITE_BARO_MAX_JUMP_MM);
    velocity_cms = (int32_t)(((int64_t)delta_mm * 100) / (int64_t)dt_ms);
    velocity_cms = Px4Lite_ClampI32(velocity_cms, -PX4LITE_BARO_MAX_VERTICAL_CMS, PX4LITE_BARO_MAX_VERTICAL_CMS);
    /* 一阶低通：新值只占 1/4 权重，压制气压噪声抖动 */
    s_baro_vertical_speed_cms += (velocity_cms - s_baro_vertical_speed_cms) / 4;
  } else {
    s_baro_vertical_speed_cms = 0;  /* 数据太旧（超过 MAX_AGE_MS），清零而不是继续按旧值外推 */
  }
  ...
}
```

`Px4Lite_BaroRead()` 把这两步串起来，`rx_sequence` 去重后才计算，避免同一份数据被重复计入速度差分：

```c
if ((snapshot.pressure_pa >= PX4LITE_BARO_PRESSURE_MIN_PA) && (snapshot.pressure_pa <= PX4LITE_BARO_PRESSURE_MAX_PA)) {
  measurement->pressure_altitude_mm = Px4Lite_BaroPressureToAltitudeMm(snapshot.pressure_pa);
  measurement->vertical_speed_cms   = Px4Lite_BaroUpdateVerticalSpeed(measurement->pressure_altitude_mm, measurement->header.sample_time_ms);
}
```

| 同上 | `PX4LITE_BARO_MAX_AGE_MS` | `2500U` | Estimator 消费时的新鲜度门限，也是垂直速度计算的"数据太旧就清零"门限 |
| 同上 | `PX4LITE_BARO_PRESSURE_MIN_PA`/`MAX_PA` | `30000.0f`/`110000.0f` | 气压合理范围，超出不计算高度/速度 |
| 同上 | `PX4LITE_BARO_SEA_LEVEL_PA` | `101325.0f` | 标准大气模型海平面气压基准 |
| 同上 | `PX4LITE_BARO_MAX_VERTICAL_CMS` | `1500` | 垂直速度限幅（cm/s） |
| 同上 | `PX4LITE_BARO_MAX_JUMP_MM` | `20000` | 单次高度跳变限幅（mm） |
| `Sensor/Src/sensor_bme280.c` | `BME280_I2C_TIMEOUT_MS` | `20U` | 常规寄存器读写单次超时 |
| `Sensor/Src/sensor_bme280.c` | `BME280_PROBE_TIMEOUT_MS` | `4U` | 地址探测（`IsDeviceReady`）超时，比常规读写短，见 §4 |
| `Sensor/Src/sensor_bme280.c` | `BME280_INIT_RETRY_MS` | `1000U` | 初始化失败后的退避间隔，避免每个 `sensor` 周期都去碰坏掉的总线 |
| `Sensor/Src/sensor_bme280.c` | `BME280_REINIT_FAIL_LIMIT` | `5U` | 已初始化后连续读失败达到此值才清 `s_initialized` 触发重新初始化 |

## 8. 异常与恢复

- 驱动只上报硬件事实与错误计数，不在驱动内判 OFFLINE/FAILED，这两个状态由 Health 统一判定。
- I2C 读写失败返回 `BME280_RESULT_IO_ERROR`，`Bme280_NoteReadFailure()` 记一次失败并把测量状态机打回
  `IDLE`；连续失败达到 `BME280_REINIT_FAIL_LIMIT`（5 次）后清除 `s_initialized`，触发重新走一遍初始化
  流程（不是无限重试同一个坏状态）。这套"连续失败计数 → 清初始化标志 → 下次 Service 重新探测"的自愈
  机制是 2026-06-12 一次真实事故修复后加上的，见 §11 案例 1，不是从一开始就有的。
- 芯片 ID 不匹配返回 `BME280_RESULT_BAD_ID`；状态位等待超时返回 `BME280_RESULT_TIMEOUT`。
- 初始化失败使用 `BME280_INIT_RETRY_MS`（1000 ms）退避，避免设备缺失或损坏时每个 `sensor` 周期都去
  阻塞 I2C 总线、拖累同总线的其他设备。
- **总线级恢复不在 BME280 驱动里，在 BSP 层**：`Bsp/Src/bsp_i2c.c` 的 `BSP_I2C_Finish()` 只在 HAL 返回
  `HAL_TIMEOUT`/`HAL_BUSY`（真正的总线卡死）时调用 `BSP_I2C_BusRecover()`（把 SCL/SDA 切开漏 GPIO 输出
  9 个时钟脉冲冲掉从机残留位、补一个 STOP、重新 `Init`）；`HAL_ERROR`（NACK）**不**触发这个恢复，因为
  NACK 是共享总线上的正常瞬态，整条总线重来反而会打断同总线上的其他设备（这条规则本身就是吸取了
  §11 案例 2 的教训后定的）。
- 热插拔恢复：`Sensor_BME280_RequestReinit()` 只置位请求标志（供 `recover` 回调调用），真正的重新
  初始化在下一次 `Service()` 顶部执行；`Px4Lite_HealthRun` 判 OFFLINE 后触发的 `recover` 回调走的就是
  这条路径。

## 9. 调试

- `DEBUG_BARO_MONITOR_ENABLE` **当前默认关闭（`0U`）**，需要现场核对 BME280 数据时手动改成 `1U` 重新
  编译；打开后按 `DEBUG_BARO_REPORT_PERIOD_MS`（1000 ms）周期打印。调试完建议改回 `0U`，不要把调试开关
  常年开着。
- 调试开关关闭后不改采集/解析/状态机/发布逻辑。
- **软硬件两侧排查手段**：软件侧——打开 `DEBUG_BARO_MONITOR_ENABLE` 看 `error_count`/`rx_sequence` 是

## 10. 验收要点

通用验收逐条对照 [15_模块接入标准与评审清单.md](../../15_模块接入标准与评审清单.md) §6，本节只写
15 里没有的、BME280 专属的关键测试用例：

| 用例 | 操作步骤 | 预期结果 | 实际结果 |
|---|---|---|---|
| 芯片 ID 不匹配 | 断开传感器或接错地址，模拟探测失败 | 初始化返回 `BME280_RESULT_BAD_ID`，`error_count++`，不进入运行状态 | |
| 强制测量超时 | 人为拖长总线响应（如降低总线速度或制造总线拥塞） | 超过 `BME280_MEASURE_TIMEOUT_MS`（30ms）判超时，状态机回 `IDLE` 重新触发，不产出脏数据 | |
| 连续失败触发重初始化 | 持续制造 I2C 失败直到达到 `BME280_REINIT_FAIL_LIMIT`（5 次） | `s_initialized` 清零，下次 Service 重新走探测→ID→校准的完整初始化流程 | |
| 气压超出合理范围 | 人为构造超出 `[30000,110000]Pa` 的数值（如极端环境模拟或篡改数据） | `pressure_altitude_mm`/`vertical_speed_cms` 不计算，保持上次有效值不被污染 | |
| 高度跳变限幅 | 人为构造单次高度跳变超过 20000mm 的相邻两帧数据 | `vertical_speed_cms` 被限幅在 `±PX4LITE_BARO_MAX_VERTICAL_CMS`（1500cm/s）内，不产出离谱速度值 | |
| I2C1 共总线互不影响 | BME280 与 MPU6050 同时长时间运行 | 两者各自 `error_count` 不应显著增长，一方故障不拖累另一方 | |

## 11. 开发踩坑与教学案例

> 本节前两条摘自本工程真实的联调事故记录（`Development_Guide/Change_History/`），不是编的场景；
> 第三条明确标注为"未确认过的推测性风险点"，不是真实事故，两者不要混为一谈。

**问题 1（真实事故）：I2C 用 HAL 轮询忙等 + 无总线恢复逻辑，插上传感器后整个屏幕卡死**（类别：软硬件
结合；完整记录见 [`2026-06-12_21_I2C阻塞与显示卡死修复.md`](../Change_History/2026-06-12_21_I2C阻塞与显示卡死修复.md)）

- **现象**：不接 I2C 传感器时显示刷新正常；接入传感器（当时是 MPU6050 和 BME280）后屏幕刷新卡住。
- **定位**：对照任务优先级配置——`sensor` 任务最高优先级（`idle+4`），`biz_display` 最低（`idle+1`）；
  排查 `Bsp/Src/bsp_i2c.c` 发现传感器读取走 `HAL_I2C_*` 轮询接口，HAL 轮询版 I2C 是**忙等，不让出 CPU**；
  再看驱动发现未初始化成功时**每个 10ms 服务周期都重新探测 + 阻塞 I2C**；`bsp_i2c.c` 当时**没有任何
  总线恢复逻辑**。四条叠加：总线一旦被钳死或时钟拉伸，最高优先级的 `sensor` 任务长时间忙等在 I2C 上，
  把最低优先级的显示任务活活饿死。
- **根因**：任务优先级设计本身没错（`sensor` 就应该最高优先级），错在**没有给这个最高优先级任务的
  阻塞总线操作设上限**——没有超时收紧、没有总线恢复、没有失败退避，三重缺失叠在一起，一旦总线状态
  不干净就会无限期忙等。
- **解法**（四步，都在 `bsp_i2c.c`/`sensor_bme280.c`/`sensor_mpu6050.c`）：① `bsp_i2c.c` 新增
  `BSP_I2C_BusRecover()`（SCL/SDA 切开漏 GPIO 冲 9 个时钟脉冲、补 STOP、重新 `Init`），只在
  `HAL_TIMEOUT`/`HAL_BUSY` 时触发，`HAL_ERROR`(NACK) 不触发（NACK 是共享总线正常瞬态，整条总线重来
  反而打断另一个传感器）；② 收紧探测超时（新增 `BME280_PROBE_TIMEOUT_MS=4`，地址探测失败时快速跳过，
  常规读写超时 `BME280_I2C_TIMEOUT_MS` 保持 20），把单次最坏忙等时间限住；③ 初始化失败退避
  `*_INIT_RETRY_MS`（1000ms），器件缺失时每秒最多碰一次总线；④ 初始化
  成功后连续读失败达到 `*_REINIT_FAIL_LIMIT`（5 次）才清 `s_initialized` 重新初始化，解决供电抖动复位
  后"一直读一个不再采样的芯片、表现为连接不稳定"的问题。
- **教学点 / 学生易错**：给任务定优先级时容易只想"这个任务重要所以给最高优先级"，忽略了"这个任务里
  会不会有无上限的阻塞操作"——高优先级 + 无界阻塞是最容易饿死低优先级任务的组合，比低优先级任务本身
  的问题更隐蔽，因为现象是"不相关的另一个任务卡死"，直觉上不会先怀疑到高优先级任务头上。
- **✅ 原"20 → 4"疑点已查明**：历史记录写"`BME280_I2C_TIMEOUT_MS` 20 → 4"，核对源码后确认那个"4"其实
  落在新增的 `BME280_PROBE_TIMEOUT_MS`（探测超时）上，常规读写超时 `BME280_I2C_TIMEOUT_MS` 保持 `20U`，
  两者并存不矛盾，详见 §4/§7。

**问题 2（真实事故）：MPU6050 故障重试没有退避，拖累共用总线的 BME280 忽断忽续**（类别：软件；完整
记录见 [`2026-06-17_31_I2C共享总线与MPU6050退避说明.md`](../Change_History/2026-06-17_31_I2C共享总线与MPU6050退避说明.md)）

- **现象**：MPU6050 上电运行一段时间后离线；**BME280 会跟着短暂离线，随后又自己恢复**；看起来像两个
  传感器互相干扰，实际显示层的变量映射根本没有交叉。
- **定位**：排除显示层变量冲突后，顺着共享总线往下查：MPU6050（10ms 周期，单次 I2C 超时 20ms）发生
  I2C 错误后没有退避机制，下一个 10ms 周期立刻又去访问，反复触发 I2C 超时/BUSY，触发 BSP 层对**整条**
  I2C 总线做恢复；BME280（1000ms 周期）挂在同一条总线上，因此被短时间牵连。
- **根因**：这不是硬件问题，是**软件层面缺少故障退避**——单个设备的高频重试失败会通过"整条总线恢复"
  这个共享动作波及总线上的其他设备，设备越是高频访问、故障退避越缺失，波及范围越大越频繁。
- **解法**：MPU6050 发生 `PX4LITE_IO_ERROR` 后暂停访问 1000ms（退避期间不高频重试异常设备），退避
  结束后才重新探测地址、检查 `WHO_AM_I`、重新配置寄存器；退避期间 BME280 不再被 MPU6050 的失败访问
  持续干扰。
- **教学点 / 学生易错**：**这条不是硬件接线问题，硬件排查（上拉电阻/供电/接地/接触）是文档里明确列出
  的"仍需检查"的并行项，但不是这次已确认的根因**——容易一看到"总线上两个设备互相影响、时断时续"就
  条件反射去查上拉电阻和接线，实际上先看一眼"是不是某个设备在故障时疯狂重试"往往更快定位到问题。

**问题 3（推测性风险点，非真实事故——本节核对时没有找到对应的联调记录，如实标注）：补偿计算调用顺序
依赖容易被破坏**（类别：软件）

- **风险描述**：气压/湿度补偿公式依赖温度补偿计算过程中的中间量 `s_t_fine`（见 §4），如果后续维护时
  改动了三个补偿函数的调用顺序，或者在气压/湿度补偿之前插入了其他会修改 `s_t_fine` 的代码路径，算出
  来的气压/湿度数值会**形式上合理（不是 NaN 或极端值）但数值是错的**，不会报错也不会崩溃。
- **为什么值得记录**：这类"形式正确、数值错误"的 bug 比直接崩溃更难发现，常规的"程序跑起来了、有
  数据输出"这种验收方式抓不住它，必须拿已知参考值（比如对照另一个温湿度计）核算数值本身对不对。
- **教学点**：不能因为暂时没查到这个模块的真实事故记录，就假设这类风险不存在——本条的价值是提醒
  "验收要核算数值，不能只看有没有输出"，不是暗示这件事已经发生过。
