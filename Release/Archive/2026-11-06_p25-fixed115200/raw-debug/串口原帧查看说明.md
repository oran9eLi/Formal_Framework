# 串口原帧查看说明

本说明对应执行台账R52、证据V1-E48，适用于同目录的[cns-f407-p25-fixed115200-raw-20261106.hex](cns-f407-p25-fixed115200-raw-20261106.hex)。这是原帧观察版，尚未烧录实测；[父目录普通版](../MANIFEST.md)保留清屏后的正常功能。本版堆占用估算79.22%，超过75%目标，仅作短时观察，不用于长稳验收。

## 电脑怎样接收

使用现有Debug电脑串口，选择对应COM端口，参数为**115200 bit/s、8数据位、无校验、1停止位、无硬件流控**。串口工具选择文本/ASCII接收，保存文本日志；固件已把原始字节转成可读HEX，不需要再开启工具的HEX显示模式。

| 调试USART1信号 | 电脑串口侧 |
|---|---|
| PA9，TX输出 | 接3.3V TTL串口接收RX |
| GND | 共地 |
| PA10，RX输入 | 仅接收查看时可不连接电脑TX，无需发送命令 |

上述为USART1调试口；GPS自身仍使用USART2 PA2/PA3，树莓派使用USART6。这里仅接收调试文本，不向ST-Link或GPS发送设备命令。

## 怎样辨认一帧

除既有GNSS/TIME摘要外，原帧头以`GNSS-RAW sampled`开头。以下仅说明输出格式，不是实测记录：

```text
[DBG] GNSS-RAW sampled NAV-PVT seq=<槽内序号> class=01 id=07 len=<完整字节数> CRC=<OK或BAD> ms=<消费完成ms>
[DBG] RAW seq=<同序号> +<起始字节偏移> <本行最多32个原始字节的HEX>
```

`+0`表示从完整wire帧第0字节开始，后续偏移通常为`+32`、`+64`，直到输出字节合计等于头部`len`。保存该帧头和全部同序号数据行；每个HEX对代表一个原字节。UBX应包含B5 62前导、class/id、小端长度、payload和最后两字节实际校验。

`CRC=OK`表示校验通过，不保证已经定位；`CRC=BAD`仍是实际收到的坏帧字节，校验尾部没有被修正，不能用其物理量作有效测量。`ms`只是sensor消费完完整帧的服务时刻，不是GPS UTC、精确到线时刻或硬件PPS时间。

## 为什么没有输出所有帧

固件按三槽保存各类最新帧：0为NAV-PVT，1为NAV-DOP，2为其他UBX/NMEA。每秒最多挑一个新样本，轮转后再看下一类；没有新样本不重复打印。它不改变GPS配置的输出频率，但**不是全量、无损录制**，被新帧覆盖的旧样本不再输出。序号是每槽独立累计，0及回绕合法，不能跨不同类型比较序号，也不能用序号跳变直接认定UART丢帧。

完整wire帧上限392 B。UBX payload超过384 B、未完成帧及超长NMEA不会被截断成“完整原帧”输出。NMEA原始CR/LF作为`0D 0A`出现在HEX中。普通画面无定位数据也不妨碍已捕获原帧输出；没有`GNSS-RAW`新记录只说明这轮没有可输出的新槽样本，需结合已有摘要判断。

## NAV-PVT里看什么

先确认`class=01 id=07`、长度合理且`CRC=OK`。常用NAV-PVT载荷为92 B，完整wire帧100 B；旧协议84 B载荷也可能存在。下表偏移均从**payload第0字节**计算，若从完整wire开头数，需要再加6。多字节整数均为小端，I4为有符号32位补码。

| payload偏移 | 字段及含义 |
|---|---|
| 0，U4 | iTOW，导航历元的GPS周内毫秒；用于配对同一历元 |
| 11，位标志 | bit0 validDate、bit1 validTime；UTC字段须各自有效，不能由“有接收”代替 |
| 20，U1 | fixType：0无fix，1仅惯导，2二维，3三维，4 GNSS与惯导组合，5仅时间 |
| 21，位标志 | bit0 gnssFixOK，表示定位满足模块掩码；仅fixType非0不足以认定有效位置 |
| 23，U1 | numSV，参与解算的总卫星数，不是全部可见卫星数；0也可能是合法无fix状态 |
| 24 / 28，I4 | 经度 / 纬度，单位1e-7度 |
| 36，I4 | hMSL，平均海平面高度，单位mm，不能与椭球高混用 |
| 60，I4 | gSpeed，地面速度，单位mm/s |
| 64，I4 | headMot，运动航迹角，单位1e-5度，不是磁罗盘航向 |
| 78，新版本标志 | 已支持协议中的invalidLlh置位时，经纬度/高度无效；旧84 B及旧协议的保留位不能照搬解释 |

没有fix时，完整PVT仍可说明当前状态或时间事实；不能把无效坐标当真实位置。原始字段可帮助解释屏幕N/A，但本观察工具不自动替用户判定实板定位或精度已通过。

## NAV-DOP里看什么

NAV-DOP为`class=01 id=04`，payload18 B，完整wire26 B。payload偏移0的iTOW应与要比较的PVT历元一致；偏移12的U2为hDOP，数值除以100才是HDOP。偏移6的pDOP是另一种精度因子，不能替代HDOP；DOP是无量纲几何因子，不是米制定位误差。

完整协议字段可核对[u-blox原厂接口说明](https://content.u-blox.com/sites/default/files/u-blox-M10-SPG-5.10_InterfaceDescription_UBX-21035062.pdf)的NAV-PVT、NAV-DOP和UBX帧章节。该资料用于解释协议，不据此认定本批商品芯片型号。

本包主机检查两批共31项（27+4）通过、Keil全量0错误0警告；真实UART输出、定位及资源峰值尚未实测。普通版HEX为父目录`cf9371f146c5f3a1971c391dff48dc2d51810d6e2d61977e8fb6194c60129efa`，原帧观察结束后可回到普通版。
