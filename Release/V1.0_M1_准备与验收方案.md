## 1. 本轮准备目标

为 V1-M1-T01、T02、T03 明确改动职责、接口方向、执行顺序和实板验收条件。范围为 A01、A02、A14，以及心跳门限和看门狗启动前的覆盖缺口。

代码基线仍为 `develop`、`bbf917f81984cd35ad9f075d2d98f7cd981f9e90`、`v0.1.0-beta.2`。既有 `.uvprojx`、`.uvoptx` 差异保留。第 2—3 节记录实施前事实；软件实施后的结果单列于验证记录，不把历史构建当作本轮结果。

M0 中页面布局、曲线、回放等决策不阻塞本阶段准备。本阶段的电源门限、异常输出方式、启动喂狗规则与验收边界已细化到实施计划；仍需分别取得代码、构建和实板证据。

### 2.1 XRotor 20A 对方案的影响

已查阅[好盈 XRotor 8A/10A/20A/40A 官方手册](https://www.hobbywing.com/en/uploads/file/20221019/47cf36385ae0619cd18168af4f7cbb0d.pdf)（2016-12-27 版，第 1 页）。手册要求首次使用或更换控制器时校准油门行程；描述信号丢失超过 0.25 s 后切断输出，正常信号恢复后会恢复相应输出。

这些是该手册的行为说明，不是本机实测结果。当前固件的 1000/2000 μs 不能直接当作所有实物已经校准好的端点。准备验收时记录电调版本、既有校准状态、供电和电机；校准由操作者单独完成，不在普通开机流程自动输出高油门。

必须分别记录：主控撤收 PWM 的时刻、电调停止驱动的时刻、转子停转的时刻。转子惯性不计作主控程序响应时间，也不能把 PWM 已撤收写成电机已瞬间停止。

## 4. V1-M1-T01：本机电源保护脱离显示

### 4.1 推荐职责划分

```text
Sensor/Platform 发布本机 Battery2 topic
                   ↓
Control 每个控制周期评估有效性、年龄、电压与闭锁
                   ↓
清空目标/撤销自动过程 → 统一输出门禁 → PWM
                   ↓
Motor 状态经 App API 提供给界面和日志
```

推荐由已有 Control 任务维护供电闭锁：它已经负责目标和输出，可以在同一周期先判定再输出。若放在 Health，则还需处理两个任务间的闭锁更新和生效顺序；本阶段无需新增任务或电池注册表。

拟定规则：

1. 从 `Px4Lite_CopyBattery2()` 获取本机快照，检查读取结果、`header.valid`、采样年龄及电压范围；不用当前显示节点的数据或主电池状态代替。
2. 启动、数据无效/过期、供电不足和不可信电压均闭锁；首帧前不能默认允许输出。
3. 在目标计算和自动升/降速推进前应用闭锁，清空目标与自动过程；恢复只解除供电限制，必须由学生重新发起输出。
4. 各命令入口继续统一拒绝非零请求；检查“数据刚过期但控制周期未执行”的窗口，过期供电下不能先接受请求、随后又恢复旧目标。
5. UI 撤销闭锁写入权，现有 `App_SetMotorPowerInhibit()` / Framework setter 的生产调用者一起处理；测试通过 Battery2 桩输入条件，不能保留可绕过真实供电事实的测试专用开锁后门。
6. 本机页面从 Control 状态显示闭锁与拒绝原因；远端页的电压显示不参与本机门禁。保留必要保护事件，完整日志改版仍由 M3 跟踪。

### 4.2 本阶段实施参数

| 项目 | 现状 | 准备方案 |
|---|---|---|
| 运行电压 | 显示层名义门限 9900 mV，档位滞回 200 mV；实际还取决于前一档位 | 实施值：低于 9900 mV 闭锁；闭锁后达到 10100 mV 才恢复；已放行时 9900—10099 mV 保持放行 |
| 低电提示 | 10500 mV | 本轮不把提示阈值当作停机阈值 |
| 高值无效 | 当前大于 13500 mV 被视为不可信 | 实施沿用大于 13500 mV 闭锁；不得因电调支持更高电压就放开整机供电上限 |
| 样本最大年龄 | 2500 ms | 实施沿用：等于 2500 ms 有效，2501 ms 起失效；缺帧、无效帧同样闭锁 |
| 生效时延 | Control 20 ms，Battery2 1000 ms | 分别测量“新异常样本发布→撤收”和“真实电压下降→撤收”；后者包括采样与滤波，不能写成 20 ms |

拟复用 `operation_state=INHIBITED` 和 App 只读快照；如需要区分低压/过期等原因，仅增加必要的只读原因字段，不重建通用状态框架。Control 及所有命令路径应使用同一套判断，Framework 不包含 Business 头文件。

## 5. V1-M1-T02：致命异常撤收

### 5.1 两种输出策略及推荐

| 策略 | 适用与代价 |
|---|---|
| 持续写最小油门 | 与正常急停一致，但需要定时器时钟、计数和端点校准继续可信；只写比较寄存器还需检查预装载生效时机 |
| 停止脉冲并将四路信号拉低 | 减少对正常控制状态和定时器配置的依赖；电调切断依赖其失联保护，不能声称零延迟停机 |

**实施策略：正常急停/供电闭锁继续走最小脉宽；不可恢复异常使用专用 BSP 入口停止四路 PWM 并固定低电平。** 按 XRotor 20A 实物验证失联切断与复位后最小油门恢复。致命异常后不允许恢复旧波形或旧目标。

### 5.2 拟定接口与接入边界

- 在 `Bsp/Inc/bsp_pwm.h` / `Bsp/Src/bsp_pwm.c` 增加异常专用入口 `void BSP_PWM_EmergencyStop(void)`；Core 的 `Core_FatalQuiesce()` / `Core_FatalHalt()` 在现有 `main.c` 实现，使用新的最小声明头文件。
- 入口直接处理已配置的四路引脚/定时器寄存器，不依赖 HAL 句柄、tick、中断、调度器、锁或动态内存；允许早期初始化失败、部分 PWM 已启动及重复调用。
- 保留其他 GPIO 位；保证信号输出为确定低电平，不将“停计数器但引脚停在高电平”误当作安全撤收。
- Core 统一 fatal 入口在保存任务名、解引用异常栈、DMA 清理等动作之前执行撤收。覆盖 HardFault、MemManage、BusFault、UsageFault、Error_Handler、FreeRTOS assert、栈溢出、分配失败及 full assert。
- `configASSERT` 只转入最小依赖的 Core 入口，不引入 Framework/Business 链；现场记录放在撤收之后，异常停机路径不喂狗。
- 普通运行态仍保持 Control 为 PWM 所有者。fatal 入口只负责不可恢复停机，不提供正常 UI 可调用的另一套电机控制路径。

主控撤收时间拟以示波器触发点量测，建议目标为入口后 1 ms 内四路不再产生正常油门脉冲；该数值是验收目标，未实测。电调驱动切断和转子停转分别记录，不拿手册的 0.25 s 直接代替实测值。

## 6. V1-M1-T03：RTC、心跳与启动覆盖

### 6.1 RTC

- 已选 LSI 时显式启用并等待就绪；已有 LSE 时同样核对就绪，全部等待有超时。
- 保留可用备份时间；失败不得伪报有效时间，不自动清备份域掩盖故障。
- 对无时钟就绪、备份域未配置及需要切换时钟源的情况明确返回结果；正常读取仍通过既有 RTC/Time 路径。
- 验收覆盖无 LSE、VBAT 保留、VDD 重新上电、软复位和失败返回。

### 6.2 按任务周期维护心跳期限

推荐在现有固定心跳数组上增加每项期限，由任务创建/初始化者提交周期和启用情况；不新增独立任务注册体系，不让 Framework 包含 Business 配置头文件。

实施规则为 `timeout = max(500 ms, 3 × period_ms, min_timeout_ms)`：系统任务为 3000 ms，200 ms 业务采集为 600 ms，其他现有快任务为 500 ms。显示单独设最低 2000 ms，以覆盖一次有界初始化尝试和 500 ms 重试间隔；最长实际间隔仍待测。心跳时间取完成一次工作之后；外设初始化失败但有界返回也属于任务进展，不要求全部设备 ONLINE 才喂狗。

必需集合必须和实际创建任务一致，含 RPi 单独启用的 comm 情况与显示关闭情况。Debug/Storage 仍不进入集合。采用支持毫秒回绕的差值判断，分别记录首个心跳缺失和运行中超时。

全局把 500 ms 改大虽少改代码，但会同时放宽快任务故障检测，不作为推荐方案。检测到超时至硬件复位还包含 IWDG 剩余时间；现有 200 ms Control 失效检查是在任务再次运行时检查，不能当作任务永久卡死后的独立 200 ms 撤收保证。

### 6.3 启动与运行两阶段看门狗

推荐覆盖启动过程，并在运行后收紧窗口：

1. 首先捕获复位原因，在能够配置寄存器的早期启动点启动 IWDG 的启动窗口。
2. 启动窗口依据已核对的最坏有界初始化步骤配置；仅在明确的初始化进展点喂狗，不能在无期限等待循环里反复喂狗。
3. 调度器启动后，在限定窗口内收齐必需任务首个成功心跳；不能因某任务从未执行而永远不启动 IWDG。
4. 首轮健康后切换到运行窗口，后续喂狗仅由统一健康判定允许。
5. 启动/切换失败有可读结果，Error/fatal 不继续喂狗；IWDG 启动、窗口切换与刷新仍集中在 BSP，策略由上层组合。

实施配置：启动使用 256 分频 / RLR 4095，运行保留 64 分频 / RLR 1249。按 [ST 数据手册表 35](https://www.st.com/resource/en/datasheet/stm32f407vg.pdf) 的 LSI 17—47 kHz 范围计算，启动约 22.31—61.68 s，运行约 1.70—4.71 s；均非本机实测。RTC 两次 5 s 时钟等待与 HAL 初始化/同步等待按不超过 12 s 加开销安排预算；具体进展点见实施计划。

调度器交接后的首轮心跳期限设为 10000 ms；到期未健康时锁定启动失败，迟到心跳不解除，硬件复位时间另受 IWDG 窗口影响。交接后关闭初始化喂狗入口，只有运行窗口配置成功才能进入正常刷新。保护从 main 的 early-start 入口起，不宣称覆盖此前的启动汇编。尚未实测的驱动/显示初始化耗时是实施验收项；若某阶段超预算，应拆分该阶段的有界步骤。

## 8. 验收用例准备

下列定义验收条件；已执行的软件部分与仍待验的硬件部分逐项列于[M1 验证记录](V1.0_M1_验证记录.md)。GPIO/PWM 波形、电调响应、复位和备份域行为必须有实板证据。

| 编号 | 场景 | 必需结果与证据 |
|---|---|---|
| M1-C01 | 启动无 Battery2 / 首帧无效 | 保持闭锁，非零目标拒绝，四路最小输出 |
| M1-C02 | 运行中低压，当前查看远端或关闭显示 | 仍按本机数据清目标并撤收；远端正常电压不能放行 |
| M1-C03 | 本机正常、远端低压 | 远端显示不改变本机供电门禁 |
| M1-C04 | Battery2 单独断采，其他传感器继续更新 | 按 Battery2 年龄闭锁，不被别的数据续期 |
| M1-C05 | 门限上下各 1 mV、滞回区、超上限、年龄边界与回绕 | 判定与冻结参数表逐项一致 |
| M1-C06 | 低压/断采恢复 | 解除供电闭锁但目标仍为零；新操作才允许输出 |
| M1-C07 | 闭锁与单路/四路/脉宽/自动过程请求相邻发生 | 无绕过、无旧目标复活，拒绝不修改已有效的其他控制状态 |
| M1-C08 | KEY1 与 UI 急停、Control 恢复 | 正常急停仍可用；恢复期间不恢复旧油门 |
| M1-C09 | 四路非零后注入各 fatal 入口 | 四路信号按策略撤收，保存入口时刻/波形；不等 IWDG 复位才变化 |
| M1-C10 | PWM 初始化前/中途、重复 fatal、异常栈不可用 | 撤收入口不依赖完整句柄或现场复制完成 |
| M1-C11 | XRotor 失联与复位恢复 | 记录失联、驱动切断和转子停转时间；恢复仅出现最小油门，不能带旧目标 |
| M1-C12 | LSE 缺席、LSI 已选、VBAT 保留及 VDD 重启 | 所选时钟重新就绪；时间有效性真实，失败可见 |
| M1-C13 | 正常 1000 ms 系统任务与其他任务组合 | 无周期性误判；记录各任务实际周期/最大心跳间隔 |
| M1-C14 | 分别停一个必需任务、缺首个心跳 | 在对应期限和硬件窗口内停止喂狗并复位，记录完整时序 |
| M1-C15 | 显示关闭、仅 RPi 通信、Control 关闭配置 | 必需集合等于实际任务；无幽灵任务或漏监控 |
| M1-C16 | 初始化卡住、最长合法初始化、调度器不启动 | 卡死有硬件兜底，合法冷启动无循环复位 |
| M1-C17 | 关闭调试器暂停影响后重测 watchdog | 记录 `BSP_WATCHDOG_FREEZE_ON_DEBUG` 与连接方式，不能用断点冻结结果冒充失效保护 |
| M1-C18 | 回归、构建和资源 | 记录真实用例/结果；Keil 0 Error(s), 0 Warning(s)，内存/栈增量可追溯 |

实板准备：拆桨固定的四路电机与 XRotor 20A、电源/电压测量工具、能覆盖四路的示波器或分次一致测试方案、调试/下载器、可观察复位原因的日志和 RTC 备份供电条件。低压测试需要独立保持主控供电，避免整机掉电掩盖保护动作。

## 9. 三个冻结点的实施取值

| 编号 | 冻结内容 | 当前结论 |
|---|---|---|
| M1-P01 | 供电门限、恢复滞回与数据年龄 | 已写入实施计划：低于 9900 mV 闭锁 / 达到 10100 mV 恢复、最大年龄 2500 ms、高于 13500 mV 无效 |

推荐执行顺序为 **T01 电源门禁 → T02 fatal 撤收 → T03 RTC/心跳/启动**。T03 内先修 RTC 和心跳判定，再接入早期 watchdog，避免尚未排除的长等待形成启动复位循环。每个任务分别保留软件与实板结论。
